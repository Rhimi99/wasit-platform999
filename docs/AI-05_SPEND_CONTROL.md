# AI-05 — استهلاك المزوّدين، محاسبة التكلفة، وحدود الإنفاق

> الحالة: منفَّذ ومُختبَر (22 حالة في `packages/server/tests/afc10-ai-spend.test.ts`).
> القرار المعماري: AD-057 في `docs/ARCHITECTURE_DECISIONS.md`.

## المشكلة

قبل AI-05 كان السجل يجيب «كم استهلك المستخدم» فقط. لم يكن يجيب:

- أي **وكيل** أنفق؟
- على أي **مزوّد** وأي **نموذج** فعلي (اسم النموذج عند المزوّد لا اسم الكتالوج)؟
- في أي **بيئة** (إنتاج/ديمو)؟
- وهل التكلفة **مُقاسة من المزوّد** أم **مقدَّرة** من قائمة الأسعار أم **صفر** لمحرّك محلي؟

ولم يكن هناك أي شيء يمنع مزوّدًا مدفوعًا من الاستمرار بعد بلوغ سقف.

## ما أُضيف

### 1. إسناد كل طلب

أعمدة جديدة في `ai_requests` (Migration `0043`، إضافية بحتة):

| العمود | المعنى |
| --- | --- |
| `provider_key` | المزوّد الفعلي الذي خدم الطلب (`openai`, `anthropic`, `local-heuristic`) |
| `vendor_model` | اسم النموذج كما أعاده المزوّد |
| `agent_key` | الوكيل، من `AgentRunContext` الموثوق فقط |
| `environment` | بيئة التشغيل لحظة الطلب |
| `cost_source` | `VENDOR` \| `ESTIMATED` \| `FREE` \| `UNKNOWN` |
| `request_key` | مفتاح idempotency اختياري (فهرس فريد) |

`cost_source` هو الفرق بين «المزوّد قال إنه كلّف 0.0042» و«حسبناه من قائمة الأسعار» — لا يُخلطان في تقرير واحد.

### 2. حدود الإنفاق

`ai_spend_limits` — صف لكل (بيئة، نطاق، هدف، دورة):

- النطاق: `GLOBAL` / `PROVIDER` / `AGENT`
- الدورة: `DAILY` / `MONTHLY`
- السقف: `max_cost` و/أو `max_requests` (كلاهما اختياري، لكن واحدًا على الأقل)
- `warn_ratio` (افتراضي 0.8) لعتبة التحذير

`ai_spend_counters` — عدّاد لكل نافذة (`environment, scope, target_key, period, period_start`).
`ai_spend_alerts` — تنبيه واحد لكل نافذة ومستوى (تحذير/حجب)، مع تدقيق.

### 3. الحجز قبل النداء

```
reserveSpend()  → صف عاد = سُمح · لا صف = رُفض
   ↓ (سُمح)
نداء المزوّد
   ↓ نجاح                    ↓ فشل
settleSpend(actual)      releaseSpend()
```

الحجز والتسوية في **عبارة SQL واحدة** لكل منهما، لذا لا يمكن لعشر محاولات متزامنة تجاوز سقف فيه ثلاثة أماكن.

### 4. ماذا يحدث عند بلوغ السقف

- افتراضيًا: ينتقل الطلب إلى المحرّك المحلي (`local-heuristic`) بتكلفة صفر، وتُسجَّل `metadata.spendLimitBlocked = { scope, targetKey, period, limitAmount, spent }`. المنتج لا يتعطّل.
- مع `allowLocalFallback: false`: `429 SPEND_LIMIT_REACHED` **قبل** أي نداء مدفوع.
- بلا سعر في `ai_models` لمزوّد مدفوع: `503` — لا تُسجَّل تكلفة صفر كاذبة.

## واجهة الإدارة

`/admin/ai` → تبويب **الاستهلاك والتكلفة**:

- نوافذ: اليوم / 7 أيام / 30 يومًا، مع اسم البيئة.
- بطاقات: الطلبات، التكلفة التقديرية، المبلغ المفوتر، الرموز.
- جدولان: الاستهلاك حسب الوكيل، وحسب المزوّد والنموذج.
- جدول الحدود مع الحالة (داخل الحد / قريب / تجاوز) وإضافة/حذف.
- قائمة التنبيهات.

المسارات (صلاحية `AI_MANAGE` أو `ADMIN_AI`):

| المسار | الغرض |
| --- | --- |
| `GET /api/admin/ai/spend?days=&environment=` | نظرة عامة + حدود + تنبيهات |
| `GET /api/admin/ai/spend/limits?environment=` | الحدود |
| `PUT /api/admin/ai/spend/limits` | إنشاء/تحديث حد (تدقيق `AI_SPEND.LIMIT_UPDATED`) |
| `DELETE /api/admin/ai/spend/limits/:id` | حذف حد (تدقيق `AI_SPEND.LIMIT_DELETED`) |

## ما لا يفعله

- لا يخزّن مطالبة ولا استجابة ولا مفتاحًا: العدّادات والمال فقط.
- لا يخترع سقفًا افتراضيًا: بيئة بلا صفوف حدود = بلا سقوف.
- لا يسمح لوكيل بقراءة `ai_requests`/`ai_usage`/`ai_budgets`/`ai_spend_*` (كلها `HARD_DENY_TABLES`).
- لا يغيّر نموذج الأموال: لا محفظة، لا رصيد، ولا مساس بـ`transaction_ledger`.
