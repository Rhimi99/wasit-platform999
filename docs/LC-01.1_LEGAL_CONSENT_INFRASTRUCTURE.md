# LC-01.1 — البنية التقنية للموافقة القانونية (Legal Consent Infrastructure)

> **الحالة:** البنية **مكتملة تقنياً**، والتفعيل الإلزامي **مُطفأ افتراضياً** بانتظار الاعتماد القانوني الخارجي. لا تُنشر أي مسودّة ولا يُسجَّل أي قبول على نص غير ساري.

## 1. الهدف

إكمال البنية التي تسجّل موافقة المستخدم على **إصدار محدّد** من كل وثيقة قانونية، وتجهيز **بوابة إلزامية قابلة للتفعيل** فور اعتماد النصوص — بحيث يكون يوم الاعتماد عملية تشغيلية (تفعيل علم + نقل الوثيقة إلى `PUBLISHED`) لا بناءً جديداً.

## 2. المكوّنات

| المكوّن | الملف | الوظيفة |
| --- | --- | --- |
| كتالوج الوثائق | `packages/server/src/lib/legal/catalogue.ts` | مصدر الحقيقة للإصدار/الحالة/تاريخ السريان. كل الوثائق `LEGAL_REVIEW_REQUIRED` بـ`effectiveDate=null`. |
| تسجيل الموافقة | `packages/server/src/modules/privacy/service.ts` → `recordLegalAcceptance` | يسجّل الإصدار + التوقيت + السياق (ip/ua/locale) في `consent_events` (append-only) + `consents` + `audit_logs`. |
| قراءة الحالة | `getAcceptedVersions` / `getPendingLegalAcceptances` / `listLegalAcceptances` | أحدث إصدار مقبول لكل وثيقة، والمطلوب (إعادة) قبوله، وسجل الموافقات. |
| البوابة الإلزامية | `packages/server/src/modules/legal/enforcement.ts` | `requireLegalAcceptance()` — مُثبَّتة على كل `/api` في `app.ts`. |
| الأسطح | `packages/server/src/modules/legal/routes.ts` | عام (المنشور فقط) + مُصادَق (حالة/سجل/تسجيل قبول). |
| الويب | `packages/web/src/pages/LegalAcceptancePage.tsx` + `/dashboard/legal` | واجهة قبول متعددة اللغات + سجل الموافقات. |

## 3. الأمان: منع التزوير وقبول الغير

- **الهوية من الجلسة حصراً:** المسار `POST /api/legal/acceptances` يسجّل دائماً باسم `ctx.user.id` (المستخدم المُصادَق). لا يوجد أي مسار يقبل `userId` من الجسم.
- **جسم صارم:** مخطط الطلب `.strict()` يرفض أي مفتاح غير معروف (مثل `userId`/`actorId`) بـ422 — فلا يمكن حتى الوصول إلى الخدمة بهوية مُنتحَلة.
- **التحقق من الإصدار:** لا يُقبل إلا إصدار الوثيقة **السارية حالياً**؛ الإصدار القديم أو المجهول أو الوثيقة غير المنشورة ⇒ 409.
- **العزل:** `listLegalAcceptances`/`getAcceptedVersions` مُقيَّدان بـ`user_id` ولا يوجد مسار بمعامل مسار يسمح بقراءة موافقات مستخدم آخر.
- **عدم التسريب:** سجل الموافقات يُرجع `documentCode/version/acceptedAt/locale` فقط، ولا يُرجع ip/user-agent المخزَّنين.

## 4. الفصل عن Cookies والتسويق

- الموافقة القانونية تُخزَّن بنوع `LEGAL_DOCUMENT` في `consent_events`، ومرآة اختيارية في `consents` بنوع الوثيقة (`TERMS`/`PRIVACY_POLICY`/`DATA_PROCESSING`/`COOKIE_POLICY`).
- قبول وثيقة قانونية **لا يمنح** موافقة Cookies أو تسويق، والعكس صحيح. (مُختبَر.)

## 5. البوابة الإلزامية (Enforcement Gate)

ثلاثة شروط **يجب أن تتحقق كلها** قبل حجب أي طلب:

1. `LEGAL_ACCEPTANCE_ENFORCEMENT=on` — **مطفأ افتراضياً**، ويُفعَّل فقط بعد الاعتماد.
2. وجود وثيقة **منشورة وسارية فعلاً** (`isAcceptable`: PUBLISHED + effectiveDate ماضٍ). مقابل المسودات، البوابة لا تفعل شيئاً حتى لو كان العلم `on`.
3. المستخدم لم يقبل الإصدار الساري.

**مسارات معفاة:** `/api/auth` (تسجيل الدخول/الخروج)، `/api/health`، `/api/legal/*`، `/api/public/legal/*` — حتى يستطيع المستخدم قراءة المطلوب وتسجيل قبوله دون أن يُقفل حسابه.

**السلوك الافتراضي المُشحون:** لا تسجيل/دخول يُحجبان، ولا قبول وهمي، ولا عرض لأي مسودّة كشرط نافذ.

### 5.1 ربط الجمهور (audience) بأدوار النظام (H1)

كل وثيقة تحمل `audience` واحداً، ويُقابله **دور نظام واحد أو أكثر**. المنطق مركزي واحد (`rolesForAudience`/`appliesToRoles` في `lib/legal/catalogue.ts`) تستخدمه البوّابة (`enforcement`) وسطح الحالة (`/api/legal/acceptances/me`) والخدمة (`getPendingLegalAcceptances`) معاً، فلا تتباين قواعد التصفية بين واجهة العرض والبوّابة.

| `audience` | أدوار النظام المطابقة | ملاحظة |
| --- | --- | --- |
| `ALL` | **كل** حساب (أي دور) | لا يُعفى أي دور من وثائق `ALL`، بما فيها دور لم يُعدَّد بعد |
| `BUYER` | `CUSTOMER` | المشتري |
| `SELLER` | `MERCHANT` | لا يوجد دور `SELLER` مستقل؛ وثيقة الشروط الموسومة `SELLER` تلزم `MERCHANT` فقط |
| `SUPPLIER` | `SUPPLIER` | المورد |
| `COMPANY` | `COMPANY` | الشركة |
| `VISITOR` | — (لا أحد) | وثيقة الزائر تحكم الاستخدام المجهول، ولا تُطلب من حساب مُسجَّل |

- **الأدوار بلا جمهور مطابق** (`MARKETER`، وطاقم المنصة `SUPPORT`/`RISK`/`DISPUTE`/`ADMIN`/`SUPER_ADMIN`): تُطالب بوثائق `ALL` فقط، ولا تُعامَل ضمنياً كمشترٍ أو بائع أو مورد أو شركة.
- **المستخدم متعدد الأدوار:** يحصل على **اتحاد** الوثائق المطابقة لكل أدواره، بلا تكرار.
- **الجمهور من الجلسة حصراً:** تُقرأ الأدوار من `ctx.user.roles` (الجلسة الموثوقة)، ولا يُقبل `userId`/`actorId` من جسم الطلب لتحديد الجمهور.

> **تأكيد الحالة:** البوّابة ما زالت **مطفأة افتراضياً** (`LEGAL_ACCEPTANCE_ENFORCEMENT=off`)، وكل وثائق الكتالوج ما زالت **مسودّات** (`LEGAL_REVIEW_REQUIRED`، `effectiveDate=null`) وغير معتمدة قانونياً. هذا الإصلاح يضبط التصفية فقط ولا ينشر أي نصّ ولا يفعّل البوّابة.

### 5.2 شكل ردّ الحجب (403) وإعادة التوجيه في الواجهة (M2)

عند الحجب يعيد الخادم **`403` مع `error.code = LEGAL_ACCEPTANCE_REQUIRED`** ويحتفظ بحقل تفاصيل آمن:

```json
{ "error": { "code": "LEGAL_ACCEPTANCE_REQUIRED", "message": "…",
  "details": { "pending": [ { "code": "TERMS_OF_SERVICE", "version": "1.0.0", "title": { "ar": "…", "en": "…" } } ] } } }
```

- `ApiError.toBody()` يُصدر `details` **فقط** لهذا الرمز (`LEGAL_ACCEPTANCE_REQUIRED`)، فلا يتسرّب `details` لأي خطأ آخر. الحمولة مبنيّة في `enforcement.ts` من الكتالوج (code/version/title فقط) — بلا stack trace، ولا أسرار، ولا معرّفات داخلية، ولا ما يسمح للعميل بتحديد هويته أو تفاصيل موافقاته.
- **إعادة التوجيه المركزية:** عميل الـAPI الموحّد (`packages/web/src/lib/api.ts`) هو المكان الوحيد الذي يتفاعل مع هذا الخطأ؛ عند استلام `403 + LEGAL_ACCEPTANCE_REQUIRED` ينفّذ `redirectToLegalAcceptance()` نحو **`/dashboard/legal`** (المنطق الخالص في `packages/web/src/lib/legal-gate.ts`).
- **الاستثناءات التي تمنع حلقات إعادة التوجيه** (دالة `shouldRedirectToLegalAcceptance`):
  1. يجب أن يكون `statusCode === 403` **و** `code === LEGAL_ACCEPTANCE_REQUIRED` معاً — أي `403` عادي (`FORBIDDEN`/CSRF) أو `401`/MFA لا يُحوَّل.
  2. لا إعادة توجيه إذا كان المسار الحالي `/dashboard/legal` أصلاً.
  3. لا إعادة توجيه لطلبٍ هدفه سطح القبول نفسه (`/api/legal/*`) — مطابقةً لإعفاء الخادم — فلا يمكن لصفحة الموافقة أن تعيد التوجيه إلى نفسها.
- **الإبقاء على `pending`:** يبقى متاحاً في `ApiClientError.details` وفي نتيجة `apiCall(...).errorObject`، لتقرأه واجهة الموافقة القانونية عند الحاجة، دون تخزين دائم جديد.

> **تأكيد الحالة (M2):** البوّابة ما زالت **مطفأة افتراضياً** (`LEGAL_ACCEPTANCE_ENFORCEMENT=off`)، والوثائق التسع ما زالت **مسودّات** (`LEGAL_REVIEW_REQUIRED`). لا تغيير في الأدوار ولا الصلاحيات ولا سياسة `audience`، ولا نشر ولا تفعيل.

## 6. اختبار آلية التفعيل في بيئة الاختبار

بما أن كل وثائق `docs/legal` مسودات، تُختبر البوابة بوثائق **اصطناعية منشورة للاختبار فقط** (لا تُشحن في الكتالوج الإنتاجي):

- `tests/lc011-legal-consent-gate.test.ts` — منطق القرار (خالص) + ترتيب التثبيت الحقيقي (use → route): مطفأة عند `off`، لا أثر عند `on` مع مسودات فقط، حجب 403 مع وثيقة منشورة غير مقبولة، إعفاء auth/health/legal، و**تصفية الجمهور** (H1): خريطة audience→roles، لكل دور وثائقه المطابقة + `ALL`، اتحاد الأدوار المتعددة بلا تكرار، والحالات السلبية للأدوار غير المعروفة.
- `tests/lc01-legal-framework.test.ts` — تكامل ضد قاعدة حقيقية: السجل والإصدار والتوقيت، العزل بين المستخدمين، رفض التزوير (422)، بقاء التسجيل/الدخول بلا حجب، الفصل عن Cookies/التسويق، و**تصفية الجمهور على مسار القاعدة الحقيقي** + تطابق البوّابة مع سطح الـAPI للمستخدم نفسه.

**اختبارات M2 (شكل الـ403 وإعادة التوجيه المركزية):**

- خادم — `tests/lc011-legal-consent-gate.test.ts`: بقاء `details.pending` (code/version/title) في ردّ 403 الفعلي؛ خلوّه من stack/أسرار/معرّفات داخلية؛ عدم إصدار `details` لأي رمز خطأ آخر (`FORBIDDEN`/`PROHIBITED_GOODS`)؛ وعدم إصداره حين لا تفاصيل للخطأ القانوني.
- ويب — `tests/legal-gate.test.ts` (15 اختباراً): قرار خالص (يوجّه فقط عند `403 + LEGAL_ACCEPTANCE_REQUIRED`؛ لا يوجّه على `/dashboard/legal`؛ لا يوجّه لطلبات `/api/legal/*`؛ يتجاهل `403` العادي و`401`/MFA)، الأثر الجانبي (`window.location.assign('/dashboard/legal')` مرة واحدة، وno-op بلا DOM)، والتكامل عبر `request()` الحقيقي (توجيه مرة واحدة، لا توجيه على صفحة الموافقة، لا توجيه لطلب سطح القبول، وسلامة `pending` عبر `apiCall().errorObject`).

## 7. ما يبقى بانتظار المحامي وبيانات الكيان

- اعتماد النصوص التسعة ونقلها إلى `PUBLISHED` بإصدار وتاريخ سريان.
- تعبئة بيانات الكيان والقانون الحاكم والاختصاص (انظر `docs/LC-01_LEGAL_INFO_REQUIRED.md`).
- بعد ذلك فقط: `LEGAL_ACCEPTANCE_ENFORCEMENT=on`.

## 8. القيود الملتزم بها

لا Migration (استُخدمت `consents`/`consent_events`/`audit_logs` القائمة). لا Demo/إنتاج، لا معاملات حقيقية، لا نشر قانوني، لا تفعيل إلزامي للمسودات، لا Git commit/push/stage، ولا عمليات هدّامة.
