# WASIT-COPILOT-01 — طبقة التنسيق (Copilot)

> الحالة: منفَّذ ومُختبَر — `packages/server/tests/copilot-01.test.ts` (15 حالة).
> لا Migration، لا صلاحية جديدة، لا وكيل جديد، **ولا استدعاء لأي مزوّد مدفوع** في هذه البيئة.

## 1. المشكلة

المنصة فيها 20 وكيلاً متخصصاً، لكن المدير العام لا يريد أن يعرف أي وكيل ينفّذ ماذا. يريد أن يقول هدفه بلغته، ثم يستلم تقريراً واحداً. المشكلة أن «منسّق» يُبنى بسرعة يصبح إما وكيلاً 21 له صلاحيات الكل، أو مساراً موازياً يتجاوز RBAC وKill Switch وSupervisor.

## 2. القرار

**الـCopilot طبقة تنسيق مستقلة، لا وكيل.** لا منفّذ له، ولا صف في `agent_registry`، ولا يستطيع أن يكون خطوة في أي تشغيل: `agentRunRefusal(COPILOT_CATALOGUE)` يعيد `COPILOT_NOT_RUNNABLE` (مُثبت في الاختبار). هو يملك **مهارة واحدة**: تحويل طلب واحد إلى خطة على الوكلاء القائمين، ثم تفويضها عبر الخدمات القائمة، ثم تقرير.

```
طلب المدير العام (نص حر)
   │
   ├─ intent.ts   : فهم حتمي — لغة، هدف، قيود، مخرجات متوقعة، مجالات (ar/fr/en)
   ├─ planner.ts  : خطة — LLM (COPILOT_PLAN) عند وجود مزوّد، وإلا القواعد المحلية
   │                 الخطة = أسماء وكلاء + أسباب + اعتماديات فقط، لا payloads
   ▼
validatePlan (قائم)  : السجل الحقيقي + قابلية التشغيل + صلاحيات الطالب + الرسم البياني + الحجم
   ▼
planAgentRun (قائم)  : agent_run + steps، مع requiresApproval من الكتالوج
   ▼
dispatchStep (قائم)  : createAgentTask لكل خطوة جاهزة، بترتيب الاعتماديات
   ▼
buildCopilotReport   : تقرير موحّد من قاعدة البيانات (لا من نص نموذج)
```

## 3. لماذا لا يملك الـCopilot مساراً خاصاً للتنفيذ

كل خطوة تصبح `agent_task` عبر `createAgentTask`، أي أنها تخضع تلقائياً لـ: Kill Switch، صلاحيات الوكيل وقدراته، نطاق البيانات، الموافقة البشرية للوكلاء الحسّاسين، الميزانية، حارس الإنفاق، حدّ المعدل، والتدقيق. لو أضاف الـCopilot مساراً خاصاً لخسر كل ذلك في سطر واحد.

**لا حساب إداري بديل**: التخطيط والتفويض يعملان بهوية الطالب ودوره (`run.requestedBy`). لا يوجد `system` أو admin مُقحَم لتجاوز رفض صلاحية — والاختبار يُثبت أن تاجراً يطلب وكيلاً يحتاج `order:read` يُرفض 403 بلا أي صف مكتوب.

## 4. الخطة: من يكتب ماذا

| الحقل | المصدر |
| --- | --- |
| أي وكيل | النموذج (مُقيَّد بالكتالوج) أو القواعد المحلية |
| لماذا | النموذج (نص حر، للعرض فقط) |
| `input` لكل خطوة | **كود الخادم** من `domains.ts` — النموذج لا يكتب payload |
| `dependsOn` | النموذج، ثم يُتحقَّق أنها خطوات موجودة في نفس الخطة |
| `requiresApproval` | الكتالوج (لا النموذج) |
| `stepKey` | النموذج، مُطبَّع، مع رفض التكرار |

الحماية الجوهرية: **النموذج لا يستطيع تأليف مدخلات وكيل**. حتى لو حقن مستخدم تعليمات في نص الطلب، أسوأ ما يحدث هو اختيار وكيل مسموح له أصلاً.

## 5. قدرة التوليد `COPILOT_PLAN` (امتداد AI-LLM-01)

أُضيفت قدرة رابعة إلى `LLM_CAPABILITIES`، تمرّ في **نفس** `runLlmDraft`:

- **الهوية**: `agentKey = wasit-copilot`، وتطابق سياق التشغيل إلزامي.
- **النطاق**: `generationScopeFor()` يعيد للمنسّق عقداً أضيق من كل الوكلاء: `allowedTables = ['agent_catalogue']` فقط — لا جدول تجاري واحد. أي fact بمصدر آخر يُرفض 403.
- **الاستناد**: `finalizePlan` يرفض الخطة إذا ذكرت وكيلاً غير موجود في الحقائق (`ungrounded_output`)، أو تكرّر `stepKey`، أو أشارت اعتمادية إلى خطوة غير موجودة.
- **الحدود**: `LLM_TASK_LIMITS.COPILOT_PLAN` (9,000 حرف، 700 توكن، سقف 0.035$ للمهمة).
- **الانحدار**: أي رفض (لا مزوّد، حارس إنفاق، schema، وكيل مُختلق) يعود إلى الخطة الحتمية ويُسجَّل السبب في التقرير. **عمل الـCopilot لا يعتمد على المزوّد.**

## 6. فهم الطلب (Local Heuristic)

`intent.ts` حتمي بالكامل: كشف اللغة (نسبة الحروف العربية / علامات فرنسية)، استخراج الهدف (أول جملة)، القيود والمخرجات المتوقعة عبر علامات لكل لغة، والمجالات عبر `domains.ts` (كلمات مفتاحية ar/fr/en لكل وكيل).

**توضيح فقط عند نقص مؤثر**: إذا لم يُعرَف أي مجال، لا يوجد ما يُفوَّض، فيُطلب توضيح واحد. أما طلب مفهوم فيُنفَّذ ولو نقصت تفصيلة، لأن الحسم فيها لا يغيّر الخطة.

**الاعتماديات الحقيقية** (لا اختراع): فيديو تسويقي يعتمد على خطة التسويق، الاستقطاب يعتمد على بحث السوق، الامتثال يعتمد على نتائج التسوية.

## 7. التقرير الموحّد

`buildCopilotReport` يقرأ كل شيء من قاعدة البيانات:

- **الخطة**: المصدر (`llm`/`heuristic`)، سبب الانحدار، نسخة البرومبت، هل ظهرت إشارة حقن.
- **الخطوات**: الحالة من `agent_run_steps` (لا من نص النموذج)، المهمة، المحاولات، الخطأ، ملخّص المخرجات.
- **`refused`**: يُقرأ من داخل حمولة المنفّذ (`refused: true` أو `error`)، فخطوة «نجحت» لكن الوكيل رفض تُصنَّف **جزئية** لا ناجحة.
- **التصنيفات**: `completed` / `partial` / `stalled` منفصلة — لا دمج يخفي فشلاً.
- **التصعيد**: موافقة مطلوبة، فشل، أو تشغيل معلّق.
- **التكلفة**: تخطيط + تنفيذ، و`complete=false` إذا وُجدت مهمة بلا تكلفة مسجّلة (لا تُعرض صفراً كاذباً).

## 8. الحمايات الموروثة (مُختبرة)

| الحماية | كيف تُثبت |
| --- | --- |
| RBAC | تاجر يطلب وكيلاً يحتاج `order:read` → 403، صفر `agent_run`، صفر `agent_task` |
| لا تصعيد للـCopilot | `validatePlan` يرفض `wasit-copilot` و`agent-supervisor` ووكيلاً مجهولاً |
| الموافقة البشرية | `ads-agent` يبقى `PENDING` بـ`approvedBy=null` بعد `advance` ثانٍ، والتقرير يصعّده |
| Kill Switch | طلب أثناء الإيقاف → 503، صفر تشغيل |
| Supervisor | تشغيل معلّق يُغلقه `runSupervisorCycle`، والتقرير يعكس `FAILED`، والـCopilot لا يُحييه |
| حارس الإنفاق | مزوّد مدفوع بلا سقوف → لا استدعاء، خطة حتمية بسبب `spend_guard` |
| حدّ المعدل | `ai.admin.control` → 429 بعد الحد |
| منع التكرار | نفس `requestId` مرتين → نفس `runId` ونفس مهام؛ `advance` لا يضيف مهاماً |
| عزل الطلبات | طلبان متزامنان → تقريران منفصلان، لا خطوات مختلطة |

## 9. الواجهة

تبويب **Copilot** في `/admin/ai` (`components/CopilotPanel.tsx`): صندوق طلب، حالة التخطيط، جدول الخطوات (وكيل/حالة/نتيجة)، لوحة «يحتاج قرارك»، وسجل الطلبات. لا تعرض أي برومبت، ولا تعتمد أي خطوة، ولا تُعلن نجاحاً من عندها.

## 10. `DECISION REQUIRED`

1. **من يوافق على الخطوات الحسّاسة عندما يكون المدير العام هو الطالب؟** التنفيذ الحالي يفرض `approvedBy ≠ requestedBy`، فإن كان GM هو الطالب وجب أن يوافق `ADMIN` آخر. البديل: دور `GM_DELEGATE` محدود. (السلوك الحالي آمن ومُوثَّق، لا افتراض.)
2. **هل يُسمح للـCopilot بتخطيط أكثر من 6 وكلاء لطلب واحد؟** الحد الحالي 6 (وسقف الخطة 10). الرقم قرار تشغيلي لا تقني.
3. **لغة مخرجات التقرير**: التقرير حالياً بيانات منظّمة بلا نص مولَّد. هل نضيف ملخّصاً لغوياً واحداً (قدرة `COPILOT_SUMMARY`)؟ لم يُضف لتفادي تكلفة إضافية بلا قرار.
