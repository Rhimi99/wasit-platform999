## 1. الفكرة

قبل T2 كان `seller_orders.settlement_status` **لا يكتبه أي كود**: يبقى `PENDING` دائماً، والتسوية تُحدِّث حالة الطلب الأب والدفتر على مستوى الأم فقط. النتيجة أن **لا أحد يعرف أي بائع تمت تسويته فعلاً** في سلة مختلطة.

بعد T2 صار لكل بائع فرعي **سجل تسوية خاص** (`seller_settlements`)، وحالة `settlement_status` تُكتب عبر **كاتب واحد فقط** (`settleSellerSuborder`)، مع بوابة تمنع الدفع (`createPayout`) قبل تسوية الفرعية نفسها.

**مبدأ ثابت:** `Settlement ≠ Payout`. تسوية الفرعية تُثبت **الاستحقاق** فقط؛ الدفع يبقى مشروطاً بإثبات التحويل من المزوّد.

---

## 2. الكاتب الوحيد — `settleSellerSuborder`

```ts
settleSellerSuborder(db, sellerOrderId, ctx?)
  → { settled, duplicate, reason?, settlementId }
```

**الترتيب (Transaction واحدة):**

1. **قفل الفرعية أولاً** (`seller_orders ... FOR UPDATE`) — القفل الأول الثابت.
2. إن كانت `SETTLED` مسبقاً ⇒ `duplicate: true` و`ALREADY_SETTLED` (إعادة التشغيل لا-op، ليست خطأ).
3. تقييم الأهلية عبر `evaluateSuborderRow` — إن لم تكن مؤهَّلة ⇒ `settled: false` مع السبب، ويُكتب `SELLER_SETTLEMENT.REJECTED` في `audit_logs`.
4. **قفل المعاملة الأب ثانياً** (`transactions ... FOR UPDATE`) — القفل الثاني الثابت.
5. التأكد من وجود قيد `SETTLEMENT / SETTLED` على المعاملة الأب (وإلا `PARENT_TRANSACTION_NOT_SETTLED`).
6. **الإدراج في `seller_settlements`** بكل القيم مأخوذة من **صف الفرعية المقفول** لا من المستدعي: `seller_id`، `seller_type`، `currency_code`، `amount = seller_payable` (4 منازل)، وربط `parent_settlement_entry_id` بقيد الأب.
7. تحديث `seller_orders.settlement_status = 'SETTLED'` بشرط `<> 'SETTLED'` (تفادي سباق).
8. كتابة `SELLER_SETTLEMENT.CONFIRMED` في `audit_logs`.

> **ثابت:** لا كود آخر في المستودع يكتب `seller_orders.settlement_status = 'SETTLED'`. الكاتب واحد.

---

## 3. شروط الأهلية (`evaluateSuborderRow`)

| الشرط | سبب الرفض |
| --- | --- |
| `settlement_status = 'SETTLED'` مسبقاً | `ALREADY_SETTLED` |
| حالة الفرعية ليست `DELIVERED` ولا `COMPLETED` | `SUBORDER_NOT_DELIVERED` |
| الطلب الأب غير موجود | `PARENT_ORDER_NOT_PAID` |
| استرداد كامل أو جزئي، أو استرداد قيد المعالجة | `REFUND_PRESENT` |
| `orders.payment_status ≠ 'PAID'` | `PARENT_ORDER_NOT_PAID` |
| نزاع غير مغلق (`≠ CLOSED/ARCHIVED`) | `DISPUTE_OPEN` |
| لا قيد `SETTLEMENT / SETTLED` على المعاملة | `PARENT_TRANSACTION_NOT_SETTLED` |

**لماذا:** فقط سطر بائع **مُسلَّم فعلاً**، وطلبه **مدفوع**، و**لم يُسترد**، و**لا نزاع مفتوح** عليه، يكون مستحقاً للتسوية. المال يجب أن يكون لا يزال لدى WASIT.

---

## 4. الربط التلقائي عند التسليم

`updateOrderStatus` (`orders/service.ts`) — بعد **commit** نجاح الانتقال إلى `DELIVERED`:

- يجمع معرّفات الفرعيات التي **انتقلت فعلاً** بهذا الانتقال.
- يستدعي `settleSellerSuborder` لكل منها **بشكل best-effort ومتكرّر-آمن (idempotent)**.
- **لا يُفشِل** عملية التسليم إن لم تكن المعاملة الأب مُسوَّاة بعد: الفرعية تبقى `PENDING` وتُلتقط لاحقاً عبر مسار إعادة المعالجة الإداري.

> الانتقال يعمل **بعد الـcommit** تحديداً كي لا يُلغي فشلُ التسويةِ انتقالَ حالةٍ نجح أصلاً.

---

## 5. بوابة الدفع (`createPayout`)

`createPayout` صار داخل معاملة واحدة، والترتيب:

1. تحديد وحدة الدفعة (الفرعية أو الشكل القديم).
2. **قفل الفرعية** (`FOR UPDATE`) — القفل الأول.
3. **قفل المعاملة** (`FOR UPDATE`) — القفل الثاني.
4. **فحص قيد `SETTLEMENT / SETTLED` على المعاملة** أولاً ⇒ `Cannot create a payout for a transaction that is not settled`.
5. **فحص تسوية الفرعية نفسها** ⇒ `Cannot create a payout before this seller suborder is settled`.

**لماذا هذا الترتيب:** القفلان يُؤخذان **قبل** أي بوابة، بنفس ترتيب `settleSellerSuborder` (فرعية ← معاملة)، فلا يمكن أن يتغيّر ما نقرؤه تحت القرار، **ولا يمكن أن يحدث deadlock** بين المسارين. وفحص المعاملة يأتي أولاً كي تكون رسالة «المعاملة غير مسوّاة» هي الأدق عند غياب التسوية الأب.

## 6. إعادة المعالجة الإدارية (Admin re-processing)

```
POST /api/admin/finance/settlements/suborders/reconcile
Body: { orderId?: string | null }
→ [{ sellerOrderId, settled, duplicate, reason? }]
```

- الصلاحية: `COMMISSION_MANAGE` أو `PAYMENT_READ`.
- `orderId` معطى ⇒ يعالج فرعيات ذلك الطلب؛ فارغ ⇒ يعالج **كل** الفرعيات `PENDING`.
- **idempotent** ومُفصَّل: كل فرعية تُرجع حكمها، فلا تفشل الدفعة كلها بسبب فرعية واحدة عالقة.
- **لا يكتب أي قيد دفتر** — يكتفي بنسبة قيد `SETTLEMENT` الأب القائم إلى كل بائع.

## 9. القيود المتبقية

- **لا Refund على مستوى الفرعية** (M2.4): الاسترداد لا يُحدِّث `seller_orders.status`/`settlement_status` بعد.
- **إسناد `transactions.sellerId`** للبائع الأول في السلة المختلطة (M2.5، منفصل).
- **لا Wallet ولا أرصدة**؛ WASIT لا تحتفظ بأموال المستخدمين.
- **لا مزوّد خارجي فعّال**؛ `sandbox`/`manual` حصراً في بيئة الاختبار/DEMO.
- **`settlement_status` لا رجعة فيه:** لا مسار يعيد `SETTLED` إلى `PENDING` (لا reverse-settlement بعد).
