# AI-02.3 — Dispatch & Controlled Execution

**النوع:** إرسال وتنفيذ منضبط لخطوات الخطة عبر نظام المهام الحالي. **لا Supervisor كامل، لا Tool Gateway، لا Retry.**
**التاريخ:** 2026-11-06 · **الفرع:** `master` · **HEAD:** `e43dee4017d2848e37d03d13025a33890adb483f` (لم يتغيّر).

## 1. الوظيفة والموقع

خدمة مستقلة `packages/server/src/modules/ai/dispatcher.ts` تُرسل خطوة صالحة من خطة محفوظة (AI-02.2) إلى **نظام المهام الحالي** (`createAgentTask`/`decideAgentTask`)، ثم تُسجّل النتيجة على الخطوة والخطة. **لا تستدعي Executor مباشرة، ولا تُنشئ نظام مهام موازياً.**

الدوال: `dispatchStep` · `approveRunStep` · `reconcileRun` · `cancelRun` · `getRunWithSteps`.

## 2. دورة حياة الخطوة

```
PENDING ──(اعتماد بشري)──▶ READY ──(dispatchStep)──▶ RUNNING ──▶ SUCCEEDED
   │                          │                          └────▶ FAILED ──▶ SKIPPED (التابعة)
   ├──(اعتماد مطلوب)──▶ AWAITING_APPROVAL ──▶ READY
   └──(فشل تبعية / إلغاء)──▶ SKIPPED / CANCELLED
```

- الخطوة الحساسة (`requiresApproval=true`) لا تُرسل إلا بعد `approveRunStep` (PENDING/AWAITING_APPROVAL → READY).
- `SKIPPED` **ليست نجاحاً**: لا تُشبع تبعية.

## 3. آلية الربط بالمهمة (بدون Migration)

`agent_run_steps` لا يحمل عمود `task_id`، ولم نُضِف عموداً أو جدولاً. الربط يُنقل داخل `agent_tasks.input` (jsonb) بمفتاحين `__runId` و`__stepId` — متسق مع اصطلاح `__userId` القائم. كما يُخزَّن `taskId` في `agent_run_steps.result`/`error` للقراءة. **لذلك لا Migration مطلوب في هذه المرحلة**، والتحقق من التكرار يتم عبر `input->>'__stepId'`.

## 4. منع التكرار والتزامن

ثلاث طبقات:
1. **مطالبة ذرّية:** `UPDATE agent_run_steps SET status='RUNNING', attempt_count=attempt_count+1 WHERE id=? AND status IN ('PENDING','READY') RETURNING id`. قفل الصف في PostgreSQL يجعل **فائزاً واحداً فقط** عند طلبين متزامنين؛ الخاسر يحصل على 0 صفوف → `409`.
2. **فحص المهمة القائمة:** قبل الإنشاء، يُبحث عن مهمة بنفس `__stepId` → إن وُجدت، رفض (`409`) بدل إنشاء نسخة ثانية (يحمي عبر إعادة التشغيل/انقطاع الاستجابة).
3. **رفض الحالات النهائية/`RUNNING`:** خطوة `SUCCEEDED`/`SKIPPED`/`CANCELLED` أو `RUNNING` تُرفض مسبقاً.

**انقطاع الاستجابة:** لا يُفترض أن المهمة لم تُنشأ؛ يُعاد قراءة الحالة الفعلية (الخطوة/المهمة) ولا تُنشأ مهمة بديلة تلقائياً.

## 5. التبعيات والفشل

1. لا تُرسل خطوة حتى تنجح **كل** تبعياتها (SUCCEEDED فقط؛ SKIPPED لا تُحتسب).
2. عند فشل خطوة، تُعلَّم الخطوات التابعة لها **بشكل متعدٍّ** `SKIPPED` (خوارزمية انتشار على الرسم) → فشل واحد لا يُطلق سلسلة.
3. الخطوات غير المتأثرة تكمل (الخطة تسمح بذلك عبر حالاتها).
4. خطوة تنتظر موافقة تبقى متوقفة.
5. الخطوة الملغاة لا تُنفَّذ.
6. `cancelRun` يمنع أي إرسال جديد (Run → `CANCELLED`، كل الخطوات غير النهائية → `CANCELLED`).
7. **لا سياسة Retry في هذه المرحلة:** الفشل يضع الخطوة `FAILED` (قابلة نظرياً لـ`RETRYING` وفق AI-02.1، لكن لا مُعيد بعد) ويُسجَّل الحدث. موثّق كحدّ.

## 6. إكمال حالة الخطة

`reconcileRun` بعد كل خطوة:
- عند اكتمال كل الخطوات (نهائية أو `FAILED`): `RUNNING`→`AGGREGATING` ثم:
  - نجاح الكل → `COMPLETED` (يمرّ عبر `assertRunCompletion` من AI-02.1 دون تخفيف).
  - نجاح جزئي → `PARTIALLY_COMPLETED`.
  - لا نجاح → `FAILED`.
- كل الانتقالات تمرّ عبر `assertRunTransition` من AI-02.1؛ لا تجاوز.

> **ملاحظة تصميم مهمة:** AI-02.1 لا يعتبر `FAILED` حالة نهائية (لأن إعادة المحاولة ممكنة). في مرحلة بلا Retry، يُعامل `FAILED` كـ«محسوم» لإغلاق التشغيل، مع الإبقاء على حارس `COMPLETED` كما هو. هذا موثّق ولم يُخفَّف الحارس.

## 7. الموافقات البشرية (حماية AI-02.P0)

- `approveRunStep` يشترط: الخطوة تتطلب موافقة، **الموافق ≠ طالب التشغيل** (`403`)، ويملك `ai:manage`/`ADMIN`/`SUPER_ADMIN`.
- إنشاء الخطة أو إرسالها **ليس** موافقة.
- الخطوة الحساسة بعد الإرسال: `createAgentTask` تُرجع `awaiting_approval`، فيُجسر الاعتماد المسبق عبر `decideAgentTask(APPROVE)` بهوية **الموافق المسجَّل** (وليس الطالب) → لا تجاوز لـApproval Engine ولا موافقة ذاتية.

## 8. الصلاحيات والميزانية

- **صلاحيات الوكيل الفعلية هي المرجع:** يُقرأ `agent_registry` الحيّ (وجود + نشاط) + `permissionsRequired` مقابل أدوار طالب التشغيل. لا تُمنح الخطة أية أداة/صلاحية غير مسجّلة.
- لا استخدام `SUPER_ADMIN` نيابة عن الوكيل؛ التنفيذ داخل `createAgentTask` يخضع لصلاحيات الوكيل نفسها.
- **الميزانية:** `isBudgetExhausted` قبل الإنشاء → `429` (نفس نمط AI-01). لا مزوّد ولا مال.

## 9. حدود السلامة المالية/الخارجية

لا تفعيل مزوّد دفع حقيقي، لا Refund/Payout، لا Webhooks خارجية، لا حملات تسويقية حقيقية، لا نشر بيانات عامة. الوكلاء الحساسون (`sales-agent`, `ads-agent`, `b2b-agent`, `risk-agent`, `dispute-assistant`, `development-agent`) يبقون خلف بوابة الموافقة كما كانوا؛ **لم تُوسَّع صلاحيات أي وكيل**.

## 12. القيود

- `attempt_count` يزداد عند كل مطالبة؛ لا إعادة محاولة تلقائية (maxAttempts=1).
- الربط بالمهمة عبر `input.__stepId` (لا عمود مفهرس)؛ الفحص بكفاءة كافية لحجم الخطة (≤25).
- فشل الـExecutor يُسجَّل نصياً في `error`؛ لا تصنيف متقدّم للأخطاء بعد.
