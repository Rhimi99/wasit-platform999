**النوع:** مرحلة تخطيط فقط (خدمة تخطيط + تحقق + ترتيب + حفظ). **لا تنفيذ وكلاء.**
**التاريخ:** 2026-11-06 · **الفرع:** `master` · **HEAD:** `e43dee4017d2848e37d03d13025a33890adb483f` (لم يتغيّر).

## 1. وظيفة طبقة التخطيط وحدودها

تحوّل خدمة التخطيط `planAgentRun` هدفاً من المدير العام + خطوات مقترحة إلى **خطة منظمة محفوظة**: صف `agent_runs` واحد بحالة `PLANNING`، وصف `agent_run_steps` لكل خطوة، مرتبة ترتيباً طوبولوجياً حتمياً.

**حدود صريحة:**
- **لا تفهم الأهداف عبر LLM.** لا يوجد مزوّد ذكي هنا؛ المتصل يزوّد الخطوات، والخدمة تتحقق وترتّب وتحفظ. لا ندّعي قدرة غير موجودة.
- **لا تنفيذ.** لا استدعاء `executeAgentTask`، ولا Executor، ولا `dispatchStep`، ولا تشغيل مجدول. الخطة تنتهي عند `PLANNING` ولا تتقدّم إلى `DISPATCHING`/`RUNNING`.
- **الإنشاء ليس موافقة.** الخطوة الحساسة تُسجَّل `requiresApproval=true` وتبقى `PENDING` بانتظار قرار منفصل.
- **لا منح صلاحيات.** الطالب يجب أن يملك كل صلاحية يطلبها كل وكيل في الخطة.

**الموقع:** `packages/server/src/modules/ai/planner.ts` (خدمة مستقلة داخل وحدة AI، تتبع البنية الحالية).

## 2. شكل المدخلات والخطة الناتجة

**المدخل (`PlanAgentRunInput`):**
```ts
{
  runKey?: string;          // مفتاح idempotency اختياري؛ يُولَّد تلقائياً إن غاب
  title: string;            // هدف مختصر (<= 300 حرف)
  description?: string | null;
  steps: Array<{
    stepKey: string;        // فريد داخل الخطة (<= 64 حرفاً)
    agentKey: string;       // وكيل مسجّل فعلاً في agent_registry
    input: Record<string, unknown>; // كائن (<= 16KB عند التسلسل)
    priority?: number;      // عدد صحيح >= 0 (افتراضي 0)
    dependsOn?: string[];   // مفاتيح خطوات في نفس الخطة
  }>;
}
```

**الناتج (`PersistedPlan`):** `runId`, `runKey`, `status` (دائماً `PLANNING`)، و`steps[]` كل منها: `id`, `stepKey`, `agentKey`, `status` (`PENDING`)، `priority`, `dependsOn`, `requiresApproval`, `executionOrder`.

## 3. اختيار الوكلاء والتحقق من وجودهم

- يُقرأ السجل الحيّ `agent_registry` (مُزوَّد مسبقاً من `AGENT_CATALOGUE` عبر `ensureAgentRegistrySeeded`).
- **العدد المرجعي 11 وكيلاً** وفق تدقيق AI-02.P0 — والتحقق هنا يقرأ السجل الفعلي وقت التنفيذ، لا رقماً ثابتاً في الكود، فلو تغيّر الكتالوج مستقبلاً يتكيّف التحقق تلقائياً.
- يُرفض أي `agentKey` غير موجود (`UNKNOWN_AGENT`) أو غير نشط (`INACTIVE_AGENT`).
- `requiresApproval` لكل خطوة يُشتق من `agent.requiresHumanApproval` في السجل — لا يختاره المتصل.

## 4. قواعد التبعيات والترتيب الطوبولوجي

- يُعاد استخدام `assertValidDependencies` من AI-02.1 (لا آلية متعارضة): يرفض التبعية غير المعروفة، الذاتية، الدائرية (خوارزمية Kahn)، والمفاتيح المكرّرة.
- **يُعاد التحقق في كل عملية تخطيط** — لا تُوثق نتيجة سابقة.
- **الترتيب الحتمي** (`topologicalOrder`): الخطوة لا تصبح جاهزة قبل اكتمال كل تبعياتها؛ بين الجاهزات يفوز الأعلى `priority`، وعند التساوي يُفصل بـ`stepKey` تصاعدياً → **نفس المدخلات تنتج نفس الترتيب دائماً**.
- **الأولوية لا تتجاوز التبعية:** خطوة بأولوية 100 تنتظر تبعيتها ذات الأولوية 0.
- الخطة غير القابلة للترتيب (دورة) تُرفض (`CYCLE`).
- **الحفظ:** `executionOrder` **لا يُخزَّن في عمود جديد** — يُشتق حتمياً عند القراءة (`loadPlan`) من `dependsOn`+`priority`، فلا تغيير على مخطط AI-02.1.

## 5. حدود الصلاحيات والموافقات

- **لا منح صلاحيات:** كل `permissionsRequired` لكل وكيل يُفحص ضد أدوار الطالب من RBAC (`ROLE_PERMISSIONS`)؛ أي نقص → `403 FORBIDDEN`. (المسؤول `ADMIN`/`SUPER_ADMIN` يمرّ كما في `createAgentTask` القائم — لا قاعدة جديدة).
- **حماية AI-02.P0 سليمة:** منع الموافقة الذاتية في `decideAgentTask` لم يُلمس؛ اختبار AI-02.2 يثبته (الطالب لا يعتمد طلبه → `403`).
- **لا `allowReopen`** ولا أي تجاوز لآلة الحالات؛ التخطيط لا يستدعي آلة الحالات للانتقال أصلاً (يكتب `PLANNING` عند الإنشاء فقط).
- **الميزانية:** تُفحص مسبقاً عبر `isBudgetExhausted` (نفس نمط AI-01)؛ نفادها يرفض فتح خطة جديدة (`429`). لا استدعاء مزوّد ولا مال.

## 7. حالات الرفض والأخطاء

`ApiError.validation` يحمل الرسالة العامة `"Validation failed"` ويضع السبب الآلي في `fieldErrors[0].code` (العقد الحقيقي، واختباراتنا تتحقق منه):

| الرمز | الحالة |
| --- | --- |
| `REQUIRED` | خطة فارغة، `stepKey` فارغ، `title` فارغ |
| `DUPLICATE` | تكرار `stepKey` |
| `DUPLICATE_DEPENDENCY` | تكرار تبعية داخل الخطوة |
| `UNKNOWN_DEPENDENCY` | تبعية لخطوة غير موجودة |
| `SELF_DEPENDENCY` | خطوة تعتمد على نفسها |
| `CYCLE` | دورة في التبعيات |
| `UNKNOWN_AGENT` | وكيل غير مسجّل |
| `INACTIVE_AGENT` | وكيل غير نشط |
| `INVALID` | `input` غير كائن، أو `priority` غير صالح |
| `TOO_LONG` / `TOO_LARGE` | تجاوز حدود الطول/الحجم |
| `MAX_STEPS_EXCEEDED` | تجاوز 25 خطوة |
| `UNKNOWN_REQUESTER` | طالب غير موجود |
| `409 CONFLICT` | `runKey` مكرّر (idempotency) |
| `403 FORBIDDEN` | نقص صلاحية وكيل |
| `429 RATE_LIMITED` | نفاد الميزانية |

## 9. ما بقي خارج النطاق

- **AI-02.3:** الإرسال (`dispatchStep`) والتنفيذ الفعلي وربط الخطوات بـ`agent_tasks`.
- Tool Gateway، Retry/Backoff، Circuit Breaker، Kill Switch، ميزانية على مستوى التشغيل.
- واجهة إدارية جديدة، وواجهة Supervisor.
- **توليد الخطة تلقائياً من الهدف (LLM planner)** — غير موجود ولم يُختلق. الواجهة منظمة وقابلة للتحقق بانتظار مزوّد تخطيط صريح لاحقاً.
- تثبيت ترتيب الوكلاء الرسمي (AI-05).

## 10. القيود

- `executionOrder` مشتق لا مخزَّن (لا عمود جديد؛ اتساق مع مخطط AI-02.1).
- التحقق من صلاحيات الطالب يعتمد أدواره الحالية وقت التخطيط؛ تغيّرها لاحقاً يُعاد فحصه في مراحل التنفيذ.
- لا حماية من سباق `runKey` عبر نسخ متعددة إلا بقيد القاعدة الفريد (يكفي للـidempotency).
