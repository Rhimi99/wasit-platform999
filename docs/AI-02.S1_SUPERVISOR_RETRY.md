## 3. الوظائف التي تعمل فعلياً

### 3.1 خدمة `modules/ai/supervisor.ts` (جديدة)
- **قراءة**: التشغيلات الحيّة (`PLANNING/AWAITING_APPROVAL/DISPATCHING/RUNNING/PAUSED`) وخطواتها ومهامها المرتبطة.
- **تصنيف**: نشط / متعثّر (stuck/stale) / حلقة (loop) / متجاوز الميزانية (budget) / محجوب (contained).
- **قرار**: تُغذّي `recommendIntervention` (الموجودة) وتطبّق نتيجتها فقط.
- **تطبيق محدود**: الحجب عبر آلة الحالات + `Dispatcher`؛ لا إنشاء نظام مهام موازٍ، ولا `Executor` مباشر.
- **تدقيق**: كل قرار/تدخّل يُسجَّل (`AI.AGENT_RUN_CONTAINED` / `AI.AGENT_RUN_STEP_RETRY_SCHEDULED` / `AI.AGENT_RUN_STEP_RETRY_FAILED` / `AI.AGENT_RUN_SUPERVISOR_FAILED`).
- **آمن عند التكرار**: كل الكتابات شرطية (conditional) ⇒ إعادة الدورة لا تُنشئ حجباً أو إعادة محاولة مكرّرة.
- **تزامن**: الحكم **قاعدة البيانات** (قفل صف التشغيل + كتابات شرطية + مطالبة `dispatchStep` الذرّية) — **لا Mutex وحده**. حارس `createSupervisorCycleGuard()` يمنع التداخل داخل العملية فقط.
- **أخطاء جزئية**: خطوة/تشغيل فاشل لا يُسقط الدورة؛ يُعزل ويُعدّ (`errors`) ويُسجَّل.

### 3.2 سياسة إعادة المحاولة `modules/ai/retry-policy.ts` (جديدة، صرفة)
- تُقرّر إعادة محاولة **خطوة `FAILED` فقط** (أو `RETRYING` مُجدولة).
- **fail-closed** على: حالة غير فاشلة · تشغيل ملغى · تشغيل نهائي · ميزانية مستنفدة · تبعية غير `SUCCEEDED` · بلوغ سقف المحاولات.
- تُرجع `nextAttempt` و`nextMaxAttempts` (= `limits.maxAttempts`) — **بلا Migration**: تُرفع `max_attempts` في الصف ليبقى `attempt_count ≤ max_attempts` صحيحاً.

### 3.3 سطح API إداري
- `GET /api/admin/ai/supervisor/overview` — العدّادات + الحدود + آخر دورة + آخر التدخلات وأسبابها.
- `POST /api/admin/ai/supervisor/runs/:runId/contain` — حجب يدوي (جسم: `{ reason }`).

## 4. سياسة Retry وحدودها

| الشرط | القرار |
| --- | --- |
| الخطوة `FAILED` + محاولات متبقية + تبعيات `SUCCEEDED` + الميزانية متاحة + التشغيل مفتوح | **إعادة محاولة** (FAILED → RETRYING → RUNNING) |
| الخطوة `SUCCEEDED`/`SKIPPED`/`CANCELLED`/`RUNNING` | رفض (`NOT_FAILED`) |
| التشغيل `CANCELLED` | رفض (`RUN_CANCELLED`) |
| التشغيل نهائي (`COMPLETED/PARTIALLY_COMPLETED/FAILED`) | رفض (`RUN_TERMINAL`) |
| الميزانية مستنفدة | رفض (`BUDGET_EXHAUSTED`) |
| تبعية `SKIPPED` (ليست نجاحاً) أو غير مكتملة | رفض (`DEPS_UNMET`) |
| `attemptCount ≥ limits.maxAttempts` | رفض (`ATTEMPTS_EXHAUSTED`) |

**الحدود (من `DEFAULT_SUPERVISOR_LIMITS`):** `maxAttempts=3` · `stuckRuntimeSeconds=300` · `staleQueueSeconds=3600` · `maxRunCostUsd=5` · `windowSeconds=3600`.
**لا حلقة لانهائية:** سقف المحاولات هو الحدّ الصلب؛ وإن فشل الإرسال تُعاد الخطوة `FAILED` وتُستهلك المحاولة.
**تسجيل المحاولة:** `attemptCount` (رقم المحاولة)، والسبب في Audit، والوقت عبر `updatedAt`/`createdAt` في سجل التدقيق.
**ملاحظة تتبّع (بلا Migration):** لم توجد حقول محاولة منفصلة على الخطوة؛ اعتُمد `attempt_count` القائم + `max_attempts` القائم + Audit للسبب/التوقيت. لم يُخترَع تخزين بديل.

## 5. آلية الحجب والتدخل

- **حجب آلي:** عند `contain` من السياسة (stuck/stale/loop/budget) → `containRun`:
  1. قفل صف التشغيل (`SELECT … FOR UPDATE`) وإعادة فحص الحالة داخل القفل (idempotent عبر العمليات).
  2. إلغاء كل خطوة غير منتهية (`→ CANCELLED`).
  3. نقل التشغيل إلى `FAILED` عبر انتقالات مشروعة (DRAFT يمرّ `PLANNING` أولاً).
  4. Audit `AI.AGENT_RUN_CONTAINED` (السبب + الإجراء + عدد الخطوات الملغاة).
- **لا إغلاق كـ`COMPLETED` أبداً**؛ الإغلاق الناجح يبقى حصراً عبر `reconcileRun`.
- **حجب يدوي:** نفس المسار عبر المسار الإداري (`action: manual-contain`)، محروس بصلاحيات الإدارة.

## 11. المخاطر والعوائق المتبقية

1. **دلالة إغلاق التشغيل عند الفشل:** `reconcileRun` (سلوك قائم قبل هذه المهمة) يُغلق التشغيل فور حسم كل خطواته — لذا إعادة المحاولة لا تعمل إلا في تشغيل ما زالت فيه خطوة أخرى غير محسومة. موثّق كحدّ، ولم يُغيَّر سلوك الإغلاق.
