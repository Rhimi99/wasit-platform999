# AI-02.3.1 — موثوقية التنفيذ والاستعادة (Execution Reliability & Recovery)

> المرحلة التالية لـAI-02.3 (الإرسال والتنفيذ المنضبط). تعالج فجوات الموثوقية والاستعادة
> المكتشفة في تدقيق ما بعد تنفيذ AI-02.3: مزامنة حالة الخطوة مع مهمتها، استعادة الخطوات
> العالقة `RUNNING`، سدّ نافذة الانقطاع بين المطالبة وإنشاء المهمة، وحسم سياسة `FAILED`.
> **لا تغلق AI-02 بالكامل.**

---

## 1. المشكلة التي تعالجها المرحلة

`dispatchStep` (AI-02.3) ينشئ مهمة عبر `createAgentTask` ثم يكتب النتيجة على الخطوة
**بشكل متزامن**. لكن ثلاث فجوات بقيت:

| # | الفجوة | الأثر |
| --- | --- | --- |
| G1 | لا نقطة تشغيل فعلية لطبقة الإرسال (كانت مكتبة تُستدعى في الاختبارات فقط) | الطبقة غير موصولة بتشغيل التطبيق |
| G2 | لا مُزامِن/مُصلِح: خطوة عالقة `RUNNING` لا تُقارَن بمهمتها لاحقاً | خطوة عالقة بلا حل |
| G4 | نافذة انقطاع بين المطالبة (`RUNNING`) وإنشاء المهمة/كتابة النتيجة | خطوة `RUNNING` بلا مهمة، أو بلا نتيجة |

## 2. نقطة التشغيل الفعلية (§2 من الطلب)

- **أُعيد استخدام** المُجدول الداخلي القائم `packages/server/src/lib/scheduler.ts` (يستضيف أصلاً
  مهمة AI-01 `runAgentSchedules`). أُضيفت وظيفة `runAgentRunRecovery` على إيقاع مستقل.
- التوصيل في `packages/server/src/index.ts` عبر `startScheduler(...)` — بلا Worker/طابور/خدمة جديدة.
- **مُطفأة افتراضياً**: `AI_AGENT_RUNS_RECOVERY_ENABLED=false` — التنفيذ الإنتاجي التلقائي لا يبدأ
  إلا بقرار مشغّل صريح، بعد إثبات الاختبارات والضوابط.
- **لا Executor ولا نظام مهام موازٍ**: الاستعادة تقرأ المهام القائمة فقط، ولا تنشئ مهمة بلا مطالبة.

المسار الكامل: `recoverStuckSteps` → `syncStepFromTask` → (قراءة `agent_tasks` عبر `input.__stepId`)
→ `reconcileRun`. والتنفيذ الفعلي للمهام يبقى حصراً عبر `createAgentTask` → `executeAgentTask`.

## 3. المزامنة (Synchronisation) (§3 من الطلب)

`syncStepFromTask(db, stepId, audit)` — جدول القرار:

| حالة المهمة | الشرط | إجراء الخطوة |
| --- | --- | --- |
| `succeeded` / `approved` | يوجد `result` غير فارغ | → `SUCCEEDED` (مع تخزين `taskId`) |
| `succeeded` / `approved` | بلا `result` | **لا إجراء** (`success_without_result`) |
| `failed` / `rejected` | — | → `FAILED` (مع `taskId` والخطأ) |
| `queued` / `running` / `awaiting_approval` | — | **لا إجراء** (`task_in_flight`) |
| غير معروفة | — | **لا إجراء** (`task_state_unknown`) |
| لا مهمة مرتبطة | الخطوة `RUNNING` | → `FAILED` (`running_without_task`) — **لا مهمة بديلة** |
| الخطوة نهائية أو `FAILED` | — | **لا إجراء** (`already_settled`) |

- **idempotent**: لا كتابة ولا تدقيق إلا عند تغيّر فعلي؛ إعادة التشغيل لا تُكرّر Audit Events.
- لا تُعتبر المهمة المنتهية ناجحة دون نتيجة صحيحة.
- `reconcileRun` تُغلق الخطة وفق آلة حالات AI-02.1، ولا تبقى `RUNNING` بعد انتهاء كل مهامها.

## 4. استعادة الخطوات العالقة (§4 من الطلب)

`recoverStuckSteps(db, { stuckSeconds, leaseSeconds, limit }, audit)`:

1. **الاكتشاف**: خطوات `RUNNING` حيث `started_at < now() - stuckSeconds` و`updated_at < now() - leaseSeconds`.
2. **المطالبة الذرّية (إيجار)**: `UPDATE agent_run_steps SET updated_at=now() WHERE id=? AND status='RUNNING'
   AND started_at < now()-stuck AND updated_at < now()-lease RETURNING id` — **فائز واحد** فقط، فلا
   تعالج عمليتا Recovery الخطوة نفسها (مُختبَر: عمليتا Recovery متزامنتان → استعادة واحدة).
3. **قراءة حالة المهمة قبل أي إجراء** — لا إعادة إرسال لمهمة تعمل (`in_flight`).
4. نجاح → مزامنة `SUCCEEDED`؛ فشل → تسجيل `FAILED`؛ لا مهمة → `FAILED`؛ حالة مجهولة → **لا إجراء**.
5. كل قرار يُسجَّل في Audit (`AI.AGENT_RUN_STEP_RECOVERED` / `AI.AGENT_RUN_STEP_SYNCED`) مع السبب.
6. ثم `reconcileRun` لكل خطة تأثّرت.

**المهل قابلة للضبط** عبر إعداد واضح لا قيمة سحرية:
`AI_AGENT_RUN_STEP_STUCK_SECONDS` (افتراضي 300)، `AI_AGENT_RUNS_RECOVERY_INTERVAL_MINUTES` (افتراضي 5).
> **تحديث (AI-02.3.2):** أُزيل `AI_AGENT_RUNS_AUTO_DISPATCH_ENABLED` لأنه إعداد ميّت لم يُقرأ في أي مسار؛ لا Auto Dispatch معتمداً ضمن النطاق.
`recoverRun(db, runId, audit)` تُزامن خطة واحدة عند الطلب.

## 5. ذرّية Dispatch وإنشاء المهمة (§5 من الطلب)

- **الكاتب الوحيد** يبقى المطالبة الذرّية: `UPDATE agent_run_steps SET status='RUNNING' ...
  WHERE id=? AND status IN ('PENDING','READY') RETURNING id` — فائز واحد عند التزامن.
- **فحص عدم التكرار**: `findTaskForStep` يمنع إنشاء مهمة ثانية لنفس الخطوة (`input.__stepId`).
- **نافذة الانقطاع**: بما أن `createAgentTask` **ينفّذ الـExecutor متزامناً** ولا يمكن دمجه في معاملة
  المطالبة، لم تُفرض **معاملة زائفة** ولا اتصال ثانٍ غير متناسق. بدلاً منها اختير النمط الآمن المناسب:
  **Claim/Lease + Idempotent Recovery**:
  - انقطاع **بعد المطالبة وقبل إنشاء المهمة** → Recovery ترى خطوة `RUNNING` بلا مهمة → `FAILED` (لا إنشاء بديل).
  - انقطاع **بعد إنشاء المهمة وقبل كتابة النتيجة** → Recovery تقرأ المهمة وتُزامن نتيجتها.
- **بلا Migration**: لم يُضَف عمود ولا جدول ولا قيد فريد؛ المطالبة الذرّية كافية لضمان عدم التكرار.
  (قيد فريد على `input->>'__stepId'` دفاعٌ إضافي اختياري مؤجّل، لا حاجة مثبتة له الآن.)

## 6. سياسة FAILED وRETRYING (§6 من الطلب)

- **لا Retry في هذه المرحلة**: `FAILED` تبقى مسجّلة بانتظار تدخّل مخوّل، ولا تُعاد العمليات تلقائياً.
- **`maxAttempts` مفروض**: `dispatchStep` يرفض إرسال خطوة استنفدت محاولاتها (`attemptCount >= maxAttempts`).
  المُخطِّط يضع `maxAttempts=1`، فلا إعادة تنفيذ عشوائية (مُختبَر: الحالة 13).
- **`FAILED` ليست نجاحاً** و**`SKIPPED` ليست نجاحاً**: لا تُحتسب في `succeeded`، وتُغلَق الخطة
  `PARTIALLY_COMPLETED`/`FAILED` وفق التركيبة (مُختبَر: 14/15).
- **لا تُغلق الخطة `COMPLETED` مع فشل**، ولا تُغلق ما دامت هناك خطوة غير محسومة (مُختبَر: 15/16).
- كل محاولة ونتيجتها مُسجّلة (Audit + `result`/`error` + `attemptCount`).
- **إصلاح**: `reconcileRun` يمرّ الآن عبر الحالات القانونية (`PLANNING → DISPATCHING → RUNNING →
  AGGREGATING`) عند إغلاق خطة ما زالت `PLANNING` (نافذة انقطاع كشفتها حالة اختبار فعلية).

## 7. صلاحيات الوكلاء والموافقات (§7 من الطلب — إلزامي، لم يُخفَّف)

- **هوية كل وكيل مستقلة**: `agent_registry` هو المرجع؛ لا صلاحيات تُمنح من Supervisor/Recovery.
- **الصلاحيات تُفحَص عند التنفيذ الفعلي**: في `createAgentTask` (نقطة التنفيذ) وفي `dispatchStep`
  (عند الإرسال) — مُختبَر (19: سحب الدور بين التخطيط والإرسال → رفض).
- **لا تمرير صلاحيات `SUPER_ADMIN` إلى Executor**: يُمرَّر فقط `__userId` (هوية).
- **الموافقة البشرية إلزامية للخطوة الحساسة**: `dispatchStep` يرفض الخطوة الحساسة قبل `approvedBy`؛
  Recovery **لا يوافق** ولا ينتحل هوية موافق (مُختبَر: 17 — خطوة حساسة عالقة → `FAILED` مع `approvedBy=null`).
- **الطالب لا يوافق على طلبه**: حارس `approveRunStep` + `decideAgentTask` (مُختبَر: 18).
- **لا تحايل عبر خطوة أخرى**: كل خطوة تُفحَص بوكيلها وصلاحياتها.
