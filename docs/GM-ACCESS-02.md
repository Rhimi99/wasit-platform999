# GM-ACCESS-02 — تدوير كلمة مرور المدير العام

> **الحالة**: مُنفَّذ ومُتحقَّق على قاعدة اختبار معزولة — 2026-11-23
> **القرار المعماري**: AD-059
> **Migration**: **لا يحتاج** (يستخدم `users.password_hash` و`sessions` القائمين)
> **الاختبارات**: `packages/server/tests/gm-access-02.test.ts` (12 حالة)

---

## 1. لماذا هذه المهمة

`docs/GM-ACCESS-01.md` أغلق ثلاث طرق مسدودة: بوابة البريد، وفقدان جهاز TOTP، وإعادة
تسجيل العامل بجلسة مسروقة. لكنه ترك رابعًا مفتوحًا:

> **مالك المنصة لا يعرف كلمة المرور الحالية.**

كل مسارات GM-ACCESS-01 تفترض أن صاحب الحساب يملك كلمة المرور:

| المسار | يفترض | لا يفيد عندما |
| --- | --- | --- |
| رابط البريد | الوصول للبريد | البريد لا يصل |
| عامل ثانٍ مؤكَّد | جهاز TOTP + كلمة المرور | كلمة المرور مجهولة |
| تذكرة مشغّل (`issue`) | كلمة المرور | كلمة المرور مجهولة أو مسرَّبة |
| `reset-factor` | كلمة المرور | كلمة المرور مجهولة |

فإن كانت كلمة المرور هي المشكلة (نُشرت في محادثة، أو ضاعت، أو ضبطها شخص آخر)، لم يكن
أمام المالك أي إجراء. هذه المهمة تضيف الإجراء الوحيد المفقود: **استبدال كلمة مرور حساب
`SUPER_ADMIN` واحد من طرفية الخادم**.

## 2. الإجراء (CLI فقط، لا مسار HTTP)

```bash
cd packages/server
npm run gm:access -- set-password --email <بريد المدير العام> \
  --reason "سبب التغيير (١٠ أحرف على الأقل)" --confirm --generate
```

### 2.1 ما يفعله بالضبط

1. يحلّ الحساب بالبريد، ويتأكد أنه **`SUPER_ADMIN`** وأنه نشط.
2. يولّد كلمة مرور **٣٢ حرفًا** من مولّد CSPRNG (ضمان وجود الأحرف الكبيرة والصغيرة
   والأرقام والرموز، بلا أحرف متشابهة `l I 1 O 0`).
3. يكتبها إلى ملف **`0600`** داخل مجلد **`0700`** خارج أي شجرة Git
   (افتراضيًا `~/.wasit-secrets/`، أو `WASIT_SECRETS_DIR`، أو `--vault <path>`).
4. يحسب `argon2` ويكتبه في `users.password_hash` **لهذا الحساب وحده**.
5. يُبطل **كل** جلسات الحساب (`sessions.revoked_at`).
6. يكتب `audit_logs` بعملية `GM_ACCESS.PASSWORD_RESET` تحمل: السبب، اسم حساب نظام
   التشغيل، عدد الجلسات المُبطلة — **ولا تحمل كلمة المرور ولا الهاش**.
7. يطبع: البريد، عدد الجلسات المُبطلة، ومسار الملف ورمزه (`600`) — **ولا يطبع كلمة المرور**.

### 2.2 ما لا يفعله (حدود مقصودة)

| ليس | السبب |
| --- | --- |
| لا يمسّ أي حساب آخر | التحديث مقصور على صف `users` المطابق للبريد المذكور |
| لا يغيّر `email_verified` | بوابة البريد تبقى كما هي؛ التغيير لا يمنح تحققًا مجانيًا |
| لا يغيّر `mfa_enabled` ولا `authenticator_apps` | العامل الثاني يبقى فعّالًا ومطلوبًا |
| لا يغيّر `user_roles` | لا تصعيد صلاحيات بأي شكل |
| لا يفتح جلسة | لا رمز ولا كوكي في المخرجات |
| لا يقبل كلمة المرور في `argv` | `--password` مرفوض: `argv` مرئي في `ps` وفي سجل الأوامر |
| لا يكتب السر في السجل أو التدقيق | مُثبت باختبار يبحث عن السر والهاش في صفوف التدقيق |
| لا يكتب داخل شجرة Git | يرفض `--vault` داخل أي مجلد فيه `.git` |
| لا يستبدل ملفًا موجودًا | `open(..., 'wx')` يفشل بدل الكتابة فوق سر سابق |

### 2.3 مصادر كلمة المرور

| المصدر | الاستخدام |
| --- | --- |
| `--generate` | التوليد على الخادم — **المُفضَّل** |
| `--password-file <path>` | كلمة مرور جاهزة (ملف `0600` فقط، وإلا يُرفض قبل أي كتابة) |

كلمة مرور ملف `--password-file` تخضع لنفس السياسة: **≥ ٢٤ حرفًا**، أربع فئات، وليست
قيمة مرفوضة، ولا تحتوي اسم الحساب.

### 2.4 القيم المرفوضة

`Rhimi123` (الكلمة التي أُلغيت بهذه المهمة)، `Passw0rd!2026` (كلمة الـDemo المنشورة في
الوثائق)، `wasit123`، `admin123`، `changeme` — كلها مرفوضة حتى لو كان طولها كافيًا.

## 3. خطوات المالك على الحساب الفعلي

> **لم يُنفَّذ على أي قاعدة مشتركة.** الخطوات أدناه تحتاج موافقة صريحة قبل التنفيذ على
> Demo أو الإنتاج.

### 3.1 التحقق المسبق (لا يكتب شيئًا)

```bash
cd packages/server
npm run gm:access -- status --email <بريد المدير العام>
```

يجب أن يظهر `active: true` و`second factor:` بحالته الحقيقية. إن كان الحساب غير موجود
أو ليس `SUPER_ADMIN` فالأمر سيرفض قبل أي تعديل.

### 3.2 تطبيق كلمة المرور المُولَّدة مسبقًا

```bash
cd packages/server
npm run gm:access -- set-password --email <البريد> \
  --reason "تدوير كلمة مرور مسرَّبة بناءً على طلب المالك" \
  --password-file /workspace/secrets/gm-super-admin-password-<stamp>.txt --confirm
```

أو التوليد على الخادم مباشرة (لا يحتاج نقل ملف):

```bash
npm run gm:access -- set-password --email <البريد> \
  --reason "تدوير كلمة مرور مسرَّبة بناءً على طلب المالك" --confirm --generate
```

### 3.3 بعد التطبيق

1. انقل كلمة المرور إلى مدير كلمات المرور الخاص بالمالك.
2. احذف الملف: `shred -u <path>`.
3. يسجّل المالك الدخول بالبريد + كلمة المرور الجديدة.
4. **بوابة البريد باقية**: إن كان الحساب `emailVerified=false` ولا عامل مؤكَّد لديه،
   أصدر تذكرة `issue` وأدخلها في حقل «رمز استرداد إداري».
5. يسجّل عامل TOTP من `/dashboard/security` ويحفظ رموز الاسترداد العشرة.
6. يحذف الملف المؤقت ويُبلّغ عن نجاح الدخول.

## 5. ما لم يتغيّر

- بوابة التحقق البريدي لكل الحسابات، ولا استثناء بدور.
- MFA: لا تجاوز، ولا إيقاف، ولا إعادة تعيين عند تغيير كلمة المرور.
- `CUSTOMER`/`MERCHANT`/`ADMIN` لا يمكن تدوير كلمة مرورهم بهذه الأداة (403 + تدقيق).
- لا كلمة مرور مشتركة، ولا كلمة مرور افتراضية، ولا `Rhimi123`.
- لا مسار HTTP جديد، ولا صلاحية RBAC جديدة، ولا تغيير في نموذج الأموال.

## 6. قرارات معلّقة (`DECISION REQUIRED`)

1. هل تُتاح الأداة لـ`ADMIN` (بموافقة مزدوجة) أم تبقى `SUPER_ADMIN` فقط؟
2. هل يُضاف `--rotate-and-notify` يرسل تنبيهًا خارجيًا للمالك بعد التدوير؟
3. هل يُفرض انتهاء صلاحية دوري (٩٠ يومًا) لكلمة مرور `SUPER_ADMIN` مع تذكير؟
