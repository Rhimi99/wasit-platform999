## 1. التشخيص: ما كان يمنع الدخول فعلاً

المنصة **لا ترسل رمز تحقق بالبريد عند تسجيل الدخول**. لا يوجد في الكود أي مسار يرسل
رمزًا بريديًا للدخول: `sendMail` تُستدعى من موضعين فقط — رابط تأكيد الحساب عند التسجيل،
ورابط إعادة تعيين كلمة المرور. رمز الستة أرقام الوحيد في المنصة هو رمز تحقق **الهاتف**
(SMS). لذلك «الرمز الذي لا يصل» هو واحد من حالتين، وكلتاهما كانتا طريقًا مسدودًا:

### الحالة أ — بوابة التحقق البريدي (الأرجح)

في `loginUser` كان أول ما يُفحص بعد كلمة المرور:

```ts
if (!user.emailVerified && !ctx.allowUnverifiedEmail) {
  throw new ApiError(403, 'EMAIL_NOT_VERIFIED', ...);
}
```

هذا يحدث **قبل** أي خطوة أخرى، فلا يمكن حتى الوصول إلى تسجيل العامل الثاني.
والقناة الوحيدة لإشباع البوابة هي رابط يُرسَل بالبريد، لكن:

| العنصر | القيمة الافتراضية | الأثر |
| --- | --- | --- |
| `MAIL_TRANSPORT` | `log` | لا يُرسَل شيء؛ يُكتب سطر مُنقّح في stdout فقط |
| `SMTP_HOST` | فارغ | لا مزوّد بريد |
| `ALLOW_DEV_TOOLING` | `false` | `POST /api/auth/dev/verification-link` يردّ 404 |

فمن أنشأ حسابه عبر `bootstrap-super-admin` أو عبر تسجيل عادي على نشر بلا SMTP يبقى
`emailVerified=false` إلى الأبد، ولا يملك أي مسار لتصحيح ذلك. **هذا هو العطل.**

### الحالة ب — عامل ثانٍ إلزامي بلا مسار استعادة

في الإنتاج (`NODE_ENV=production` مع `STAFF_MFA_ENFORCEMENT=auto`) يُعاد من الدخول
`staff_enrollment_required` بلا جلسة، ويُطلب تسجيل TOTP. إن ضاع الجهاز ولم تُحفظ رموز
الاسترداد، لا توجد أي وسيلة استعادة يملكها المشغّل: `disable` و`recovery-codes` كلاهما
يتطلب رمزًا حاليًا. هذه أيضًا طريق مسدود، وأُغلق في نفس المهمة.

### ثغرة مجاورة كُشفت أثناء التشخيص

`POST /api/auth/mfa/enroll` كان يقبل **جلسة قائمة وحدها** ويستبدل السر. أي جلسة مسروقة
تستطيع إزاحة عامل المالك ثم تسجيل عاملها. أُغلق هذا أيضًا (البند 4).

## 2. كيف صار دخول المدير العام يعمل

البوابة **لم تُعطَّل** ولن تُعطَّل لأي حساب. ما تغيّر أن لها ثلاثة مسارات إشباع:

| المسار | الدليل المطلوب | متى يُستخدم |
| --- | --- | --- |
| رابط البريد | الوصول إلى صندوق البريد | الحالة الطبيعية |
| **عامل ثانٍ مؤكَّد** | حيازة جهاز TOTP مُسجَّل ومؤكَّد | بعد أول تسجيل ناجح — يحمي من انقطاع البريد مستقبلاً |
| **تذكرة مشغّل** | وصول إلى الخادم + اعتماد القاعدة + `--confirm` | مرة واحدة لفتح الحساب حين لا بريد ولا عامل |

كل مسار يُسجَّل في `audit_logs`، وكلها **مقيَّدة بالحساب** ولا تتجاوز عاملًا ثانيًا مُفعَّلًا.

### لماذا العامل الثاني يُشبع البوابة

حيازة عامل ثانٍ مؤكَّد دليل على السيطرة على الحساب أقوى من حيازة صندوق بريد. الشرط
يُقرأ حيًّا في كل تسجيل دخول من `authenticator_apps`:

```sql
enabled = true AND confirmed_at IS NOT NULL
```

تسجيل نصف مكتمل (سر مُولَّد بلا تأكيد) **لا** يُحتسب — مُثبت بالاختبار. وعند الإشباع
يُسجَّل `AUTH.EMAIL_VERIFIED_VIA_MFA` ويُضبط `users.email_verified = true` حتى تتفق بقية
المسارات (لا حالة نصف موثّقة).

## 3. الإجراء اليدوي الآمن (لمالك المنصة)

كل الأوامر من `packages/server` على الخادم نفسه.

### 3.1 فحص الحالة أولاً (لا يكتب شيئًا)

```bash
npm run gm:access -- status --email <بريد المدير العام>
```

يُظهر: هل الحساب نشط، هل بريده موثّق، هل لديه عامل مؤكَّد، وهل توجد تذكرة حيّة.
لا يطبع أي سر.

### 3.2 إصدار تذكرة (حين لا بريد ولا عامل)

```bash
npm run gm:access -- issue --email <البريد> \
  --reason "تعذّر وصول بريد التحقق، تم التحقق من الملكية هاتفيًا" --confirm
```

- يُطبع رمز **مرة واحدة** على طرفية المشغّل، صالح **15 دقيقة** وللاستخدام **مرة واحدة**.
- لا يُكتب في أي ملف أو سجل؛ صف التدقيق يحمل `ticketId` والسبب واسم حساب نظام التشغيل فقط.
- إصدار تذكرة جديدة يُبطل السابقة.
- الأمر **يرفض** أي حساب ليس `SUPER_ADMIN`، ويرفض أيضًا حسابًا لديه عامل مؤكَّد (لا حاجة له).

ثم يدخل المدير العام من صفحة الدخول: البريد + كلمة المرور، وبعد ظهور رسالة
`EMAIL_NOT_VERIFIED` يظهر حقل «رمز استرداد إداري» فيُدخل التذكرة هناك.

### 3.3 إن كانت كلمة المرور نفسها مجهولة أو مسرَّبة

كل ما سبق يفترض أن صاحب الحساب يملك كلمة المرور. إن لم يكن، فالإجراء في
**`docs/GM-ACCESS-02.md`**: `npm run gm:access -- set-password --email <البريد> --reason "..." --confirm --generate`
يستبدل كلمة مرور هذا الحساب فقط، ويُبطل جلساته، ولا يمسّ البريد ولا العامل الثاني.

### 3.4 إن كان الجهاز (TOTP) مفقودًا

```bash
npm run gm:access -- reset-factor --email <البريد> \
  --reason "فقدان جهاز المصادقة" --confirm
```

يحذف سجل العامل ويُبطل **كل** جلسات الحساب، ولا يمسّ كلمة المرور. بعدها يسجّل المدير
العام دخوله بكلمة المرور، ويُطلب منه تسجيل عامل جديد (QR + رموز استرداد) ويؤكّده، فتُفتح
الجلسة. لا توجد كلمة مرور مؤقتة ولا كلمة مرور مشتركة في أي خطوة.

### 3.5 بعد الدخول الأول — إلزامي

1. تسجيل عامل TOTP من `/dashboard/security` (يتطلب كلمة المرور).
2. حفظ **رموز الاسترداد العشرة** خارج الجهاز (تُعرض مرة واحدة فقط، مملّحة وأحادية الاستخدام).
3. بعد ذلك: حتى لو انقطع البريد، الدخول يعمل بالعامل الثاني، ولا حاجة لتذكرة.

## 4. ما أُغلق إلى جانب ذلك

- **إعادة إثبات الهوية قبل تغيير العامل**: `POST /api/auth/mfa/enroll` يتطلب كلمة المرور
  دائمًا، ورمزًا حاليًا (TOTP أو رمز استرداد) إن كان العامل مُفعَّلًا. جلسة مسروقة لم تعد تكفي.
- **إبطال الجلسات عند تغيير العامل**: التفعيل/التعطيل/توليد رموز الاسترداد تُبطل كل الجلسات
  الأخرى للحساب وتُبقي الجلسة الطالبة. الجلسات التي أُذِن لها بالعامل القديم لا تبقى صالحة بعده.
- **رموز الاسترداد**: مملّحة `salt:hash`، مقارنة ثابتة الزمن، **أحادية الاستخدام** — أُضيف
  اختبار استخدام مزدوج عبر `/api/auth/mfa/challenge` الحقيقي.

---

## 5. ما لم يتغيّر (حدود مقصودة)

- نظام التحقق بالبريد **باقٍ** لكل الحسابات، ولم يُضَف أي استثناء بدور.
- `CUSTOMER`/`MERCHANT`/`SUPPORT`/`ADMIN` **لا** يمكنهم الحصول على تذكرة، ولا ترتفع أدوارهم.
- التذكرة لا تُصدر جلسة، ولا تتجاوز TOTP، ولا تعيد تعيين كلمة مرور، ولا تمنح دورًا.
- لا مسار HTTP يولّد تذكرة؛ المولّد الوحيد هو CLI على الخادم.
- قاعدة Demo لم تُمسّ، ولم تُغيَّر أي كلمة مرور في هذه المهمة.
