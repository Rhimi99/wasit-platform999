## 2. Executive Summary

**ما هي WASIT؟**
WASIT BUSINESS GLOBAL (الوسيط للتجارة الرقمية) هي منصة وساطة تجارية رقمية متعددة الأطراف، تجمع في نظام واحد: السوق (Marketplace)، الطلبات، المدفوعات، العمولة، دفتر الحسابات (Ledger)، التسوية (Settlement)، الصرف (Payout)، الاشتراكات، الإعلانات، التوثيق، الثقة، المخاطر، النزاعات، التحليلات، والذكاء الاصطناعي — مع إدارة مركزية كاملة (Admin) وصلاحيات دقيقة (RBAC).

**ما السوق الذي تستهدفه؟**
B2B و B2C في آنٍ واحد. البنية مبنية **Global-first**: الدول واللغات والعملات كيانات قابلة للتكوين في قاعدة البيانات، ولا توجد دولة أو لغة مُثبّتة في صميم النظام (Core). الإطلاق المرجعي الحالي محوره تونس (`TN` هي الدولة الفعّالة الوحيدة في بيانات العرض)، والتوسع إلى أسواق أخرى ممكن تقنيًا لكنه مشروط بجاهزية كل سوق ومتطلباته التشغيلية والقانونية.

**من تربط؟**
`Buyer ↔ WASIT ↔ Seller / Supplier / Company` — أي مشترٍ من جهة، ومورّد/تاجر/شركة من جهة، وWASIT في المنتصف كوسيط رقمي منظّم يدير الصفقة والعمولة والتدقيق.

**كيف تحقق الإيرادات؟**
أربعة مصادر مُنَمذجة في النظام: (1) **العمولة** — النموذج الأساسي **4% من قيمة الصفقة، مقسّمة 2% على البائع + 2% على المشتري**، وهي سياسة في قاعدة البيانات وليست مُثبّتة في الكود؛ (2) **رسوم معالجة الدفع** — منفصلة تمامًا عن العمولة؛ (3) **الإعلانات** — حملات وميزانيات؛ (4) **الاشتراكات** — خطط شهرية قابلة للتعديل إداريًا.

**ما الذي تم بناؤه؟**
النظام مُنفَّذ فعليًا: 36 وحدة برمجية (Module) في الـ Backend، 42 نقطة تركيب مسارات، 94 جدولًا في قاعدة البيانات، 28 ملف تهجير (Migration)، وواجهة React تغطي 61 ملف صفحات مع أكثر من 60 مسارًا للمستخدم (Customer / Merchant / Supplier / Company / Admin).

**ما المرحلة الحالية؟**
المنصة في **مرحلة التحقق والتثبيت التقني (Platform Validation)**. الوظائف الأساسية مبنية ومختبرة على قاعدة بيانات حقيقية، والمنصة تعمل فعليًا في بيئة عرض تجريبية. ما تبقّى أساسًا ليس "بناء وظائف" بل **جهوزية الإنتاج**: تكوين مزوّدي الدفع والبريد والرسائل والذكاء الاصطناعي الخارجيين، البنية التحتية المستضافة، والمراجعة القانونية والتجارية.

**وما نوع الشراكات المطلوبة؟**
شراكات تضيف قيمة حقيقية: خبرة في التجارة الدولية والـB2B، علاقات تجارية وأسواق، خبرة في المدفوعات والامتثال، اللوجستيك وسلاسل التوريد، التوسع الدولي، والتقنية/الذكاء الاصطناعي — إلى جانب التمويل حيث يلزم.

## 3. The Problem — المشكلة

WASIT تستهدف فجوات تشغيلية حقيقية في التجارة الرقمية بين الأطراف، وخصوصًا:

**1) صعوبة الوصول إلى مورّدين وأسواق جديدة.**
التاجر أو الشركة يحتاج إلى قنوات منظّمة للوصول إلى مورّدين ومشترين خارج دائرته المباشرة، والاعتماد على العلاقات الشخصية لا يتوسّع.

**2) تشتّت عمليات التجارة.**
دورة الصفقة تتوزّع عادة بين أدوات منفصلة: عرض المنتج، التفاوض، الطلب، الفاتورة، الدفع، ثم التسوية — بلا نظام واحد يحفظ الأثر ويربط الأطراف.

**3) ضعف الثقة بين الأطراف.**
الطرفان يحتاجان إلى إشارات ثقة قابلة للتفسير (Trust) وإلى توثيق (Verification) قبل الالتزام، وإلى مسار منظّم عند الخلاف.

**4) صعوبة الوصول إلى فرص B2B.**
الفرص بين الأعمال تحتاج مطابقة (Matching) وتصنيفًا وبحثًا موحّدًا، لا إعلانات متفرقة.

**5) الحاجة إلى وسيط رقمي منظّم.**
وجود طرف ثالث يدير القواعد (سياسة العمولة، حدود التوثيق، المخاطر، النزاعات) ويُسجّل كل تغيير في سجل تدقيق (Audit Trail) يقلّل الاحتكاك ويرفع المساءلة.

**6) الحاجة إلى أدوات تحقق ومخاطر وعمولات وتسويات منظّمة.**
احتساب العمولة يجب أن يكون بقاعدة واضحة قابلة للتدقيق، والدفع يجب أن يكون مفصولًا عن التسوية وعن العمولة، والحركة المالية يجب أن تُسجَّل بأطرافها (Payer / Beneficiary).

> **ملاحظة مصداقية:** لا تتضمّن هذه الوثيقة أي إحصاءات سوقية أو أرقام نمو، لأن المشروع لا يحتوي على دراسة سوق موثّقة. المشكلة أعلاه موصوفة من زاوية تشغيلية، لا تسويقية.

## 4. The WASIT Solution — الحل

**الحل في جملة:** طبقة وساطة رقمية واحدة تُدير دورة الصفقة كاملة بين المشتري والبائع، بقواعد معلنة وقابلة للتدقيق، وبتسجيل كامل لكل حركة مالية.

```
        ┌───────────────────────────────────────────────┐
        │              WASIT BUSINESS GLOBAL             │
        │   الوسيط التجاري الرقمي — طبقة الوساطة         │
        │                                               │
        │  Marketplace · Orders · Commission · Payments │
        │  Ledger · Settlement · Payout · Trust · Risk  │
        │  Disputes · Ads · Subscriptions · AI · Admin  │
        └───────────────────────────────────────────────┘
             ▲                                   ▲
             │                                   │
      ┌──────┴───────┐                    ┌──────┴──────────────┐
      │    Buyer     │                    │ Seller / Supplier / │
      │  (B2B/B2C)   │                    │      Company        │
      └──────────────┘                    └─────────────────────┘
```

**حدود الدور — مهم للتوضيح:**
- WASIT **منصة وسيط تجاري رقمي**. ليست شركة توصيل، وليست طرفًا لوجستيًا، وليست ناقلًا للمال بمعنى البنك.
- **لا Wallet**: النظام لا يحتفظ بأرصدة للعملاء. يسجّل الوسطاء والعمولات والرسوم فقط — وهذا قرار معماري مقصود يبسّط الإشراف ويقلّل المخاطر القانونية (موثّق في `docs/REVENUE_MODEL.md`).
- WASIT **لا تتحمّل تلقائيًا مسؤولية** أي عملية لوجستية أو أي اتفاق يُعقد خارج المنصة.
- القواعد التجارية (العمولة، الحدود، التوثيق، المخاطر، النزاعات، الإعلانات، الاشتراكات) موجودة في **محرّك سياسات (Policy Engine)** داخل قاعدة البيانات، وليست مُثبّتة في الكود — أي أنها قابلة للتعديل إداريًا مع تسجيل التغيير في سجل التدقيق.

## 5. How WASIT Works — كيف تعمل

رحلة الصفقة في النظام، بالمصطلحات الفعلية المستخدمة في المنصة:

```
Registration  →  Verification  →  Product / Offer  →  Order
      →  Commission Calculation  →  Payment  →  Ledger
      →  Settlement  →  Payout
```

| المرحلة | ما يحدث فعليًا | الحالة |
| --- | --- | --- |
| **Registration** | إنشاء الحساب، إصدار جلسة آمنة، تعيين الأدوار | BUILT / TESTED |
| **Verification** | طلب توثيق بمستويات (BASIC / VERIFIED / BUSINESS_VERIFIED / INTERNATIONAL_VERIFIED) وسياسات توثيق | BUILT / DEMO |
| **Product / Offer** | إنشاء المنتج وتعديله ونشره مع MOQ وتصنيف ومخزون | BUILT / TESTED |
| **Order** | إنشاء الطلب مع التحقق من الحد الأدنى للكمية (MOQ) والأطراف | BUILT / TESTED |
| **Commission Calculation** | قراءة سياسة العمولة الفعّالة من قاعدة البيانات واحتساب حصة البائع والمشتري | BUILT / TESTED |
| **Payment** | إنشاء نية دفع (Payment Intent) ثم تأكيد عبر مزوّد الدفع أو Webhook موقّع | BUILT / DEMO (مزوّد خارجي = CONFIGURATION REQUIRED) |
| **Ledger** | تسجيل `TRANSACTION_VALUE` و `COMMISSION` و `PAYMENT_FEE` بأطرافها (Payer / Beneficiary) | BUILT / TESTED |
| **Settlement** | تأكيد تسوية الأموال بين المنصة والبائع، مع منع أي تسوية غير مُسندة بدليل | BUILT / TESTED |
| **Payout** | صرف مستحقّ البائع عبر مزوّد صرف، مع مزامنة حالة الصرف | BUILT / DEMO |

**مبدأ مالي محفوظ:** الدفع ≠ التسوية ≠ العمولة المستحقة ≠ العمولة المستلمة. هذه **أربع حالات منفصلة** بانتقالات مستقلة، ولا يجوز دمجها في علامة "مدفوع" واحدة. النظام مُختبر على أنه **لا يفبرك** حالة `SETTLED` أو `RECEIVED` أو صرفًا مكتملًا.

## 6. Business Model — نموذج الإيرادات

### 6.1 العمولة (Commission) — المصدر الأساسي

**النموذج:** **4% من قيمة الصفقة إجمالًا**، مقسّمة:

- **2% على البائع (Seller)**
- **2% على المشتري (Buyer)**

**حقائق مُتحقَّق منها:**
- السياسة **مخزّنة في قاعدة البيانات** في جدول `commission_policies` بالقيم: `rate = 0.04`, `seller_rate = 0.02`, `buyer_rate = 0.02` — وليست مُثبّتة في الكود.
- المحرّك **يفشل مغلقًا (Fails Closed)**: إذا لم تُطابق أي سياسة فعّالة، يُرجع الخطأ `COMMISSION_POLICY_MISSING` (HTTP 422) بدل اختراع رقم.
- **لا توجد عمولة WASIT أساسية إضافية**.
- **رسوم مزوّد الدفع منفصلة تمامًا** عن عمولة WASIT، ولها جدولها الخاص `payment_fee_policies`.

**مثال رقمي حقيقي من بيانات المنصة** (طلب فعلي مُسجَّل):

| البند | القيمة |
| --- | --- |
| قيمة المنتجات (`items_total`) | 210.0000 |
| العمولة الإجمالية (`commission`) — 4% | 8.4000 |
| حصة المشتري (`buyer_commission`) — 2% | 4.2000 |
| الإجمالي النهائي (`grand_total`) | 214.2000 |

> الأرقام أعلاه مأخوذة من طلب حقيقي في قاعدة بيانات العرض، وليست تقديرية.

### 6.2 مصادر الإيراد الأخرى (مُنَمذجة)

| المصدر | الوصف | الحالة |
| --- | --- | --- |
| **رسوم معالجة الدفع** | منفصلة عن العمولة، من `payment_fee_policies`، مع شفافية Payer/Beneficiary لكل حركة | BUILT / DEMO |
| **الإعلانات** | حملات إعلانية (Product/Store/Supplier/Company Ads) + ميزانيات + إحصاءات | BUILT / DEMO |
| **الاشتراكات** | خطط شهرية قابلة للتعديل من الإدارة | BUILT / DEMO |
| **AI (مستقبلي)** | ميزانيات وحدود استخدام AI حسب الاشتراك | BUILT جزئيًا / PLANNED تجاريًا |

**خطط الاشتراك المُهيّأة فعليًا في بيانات العرض:**

| الخطة | الكود | الشريحة | السعر الشهري |
| --- | --- | --- | --- |
| Customer Free | `CUSTOMER_FREE` | CUSTOMER | 0.0000 TND |
| Small Merchant | `SMALL_MERCHANT` | MERCHANT | 19.0000 TND |
| Company | `COMPANY` | COMPANY | 99.0000 TND |
| Pro Max | `PRO_MAX` | GLOBAL | 299.0000 TND |

> **تحذير مصداقية:** هذه **أسعار تهيئة (Seed) قابلة للتعديل إداريًا**، وليست عرضًا تجاريًا نهائيًا. لا تتضمّن هذه الوثيقة أي توقّع لـ GMV أو إيرادات مستقبلية، لأن المشروع لا يحتوي على نموذج مالي مُعتمد.

## 7. Marketplace Model — نموذج السوق

**الشريحتان:** B2B و B2C في منصة واحدة.

**الأطراف والعلاقة:**

| الطرف | الدور في المنصة |
| --- | --- |
| **Buyer / Customer** | يتصفّح، يبحث، يقارن الأسعار، ينشئ الطلب، يدفع، يتابع طلباته |
| **Merchant (التاجر)** | يعرض منتجاته، يدير المخزون، يستقبل الطلبات، يشغّل الإعلانات والاشتراك |
| **Supplier (المورّد)** | يوفر المنتجات بالجملة، يربط التجار بالمصدر |
| **Company (الشركة)** | كيان تجاري أوسع للمشتريات والعلاقات B2B |
| **WASIT** | الوسيط: قواعد، عمولة، تدقيق، ثقة، مخاطر، نزاعات، تسوية |

**البنية الدولية:**
النظام مبني ليدعم تعدد الدول واللغات والعملات كبيانات لا ككود. في بيانات العرض الحالية: دولتان مُهيّأتان (`TN` فعّالة، `FR` غير فعّالة)، وثلاث لغات (`ar` بترتيب RTL افتراضي، `fr`، `en`)، مع محرّك عملات.

**التوسع الدولي** يتم **تدريجيًا** حسب جاهزية كل سوق ومتطلباته التشغيلية والقانونية — لا يوجد إطلاق جماعي مخطط له.

**ضوابط إلزامية مُنفَّذة:**
- كل وكيل **يرث صلاحيات المستخدم** — لا يتجاوزها. أي أداة تتحقق عبر RBAC قبل التنفيذ.
- الوكلاء الذين قد تمسّ قدراتهم إجراءات مالية/إدارية **مُقيَّدون بموافقة بشرية صريحة** قبل التنفيذ.
- كل مهمة وكيل تُسجَّل في سجل التدقيق (`AI.AGENT_TASK_CREATED` / `SUCCEEDED` / `FAILED` / `APPROVED` / `REJECTED`).
- **تحكم تكلفة**: جداول ميزانيات (`aiBudgets`) واستخدام (`aiRequests` / `aiUsage`) وحدود يومية حسب الاشتراك.

### 9.2 مزوّد الذكاء الاصطناعي — CONFIGURATION REQUIRED

الطبقة **مزوّد-محايدة (Provider-agnostic)** بثلاثة خيارات:

| المزوّد | الحالة |
| --- | --- |
| `local-heuristic` | **يعمل بلا تكلفة وبلا مفاتيح** — وهو المستخدم في بيئة العرض |
| `openai` (OpenAI-compatible) | **يحتاج `AI_API_KEY`** وضبط مزوّد/طراز |
| `anthropic` | **يحتاج `AI_API_KEY`** وضبط مزوّد/طراز |

> **مهم:** الذكاء الاصطناعي **لا يعمل بمزوّد خارجي في الإنتاج** إلا بعد إدخال مفاتيح المزوّد. في بيئة العرض يعمل بالمحرّك المحلي (`local-heuristic`) وهو محرّك حقيقي بلا تكلفة، لكنه ليس نموذجًا لغويًا كبيرًا.

### 9.3 WASIT AI Copilot — PLANNED (غير منفَّذ)

**Copilot ليس وكيلًا جديدًا**، بل **طبقة تنسيق ومحادثة (Orchestration / Conversational Layer)** فوق الوكلاء الحاليين: يستدعي وكيلًا واحدًا أو عدة وكلاء حسب المهمة ويجمّع نتائجهم، دون حذف أو دمج أي وكيل.

**حالته الحقيقية:** **مواصفة تصميمية فقط — لا كود، لا مسارات (Routes)، لا واجهة.** موثّق صراحة في `docs/AI_ARCHITECTURE.md` §6.5 و`docs/ARCHITECTURE_DECISIONS.md` (AD-043)، ومُصنَّف "غير منفَّذ ولا مُقنَّن في أي Phase".

> **قاعدة مصداقية:** لا يجوز عرض Copilot كميزة مُسلَّمة. الوكلاء الأحد عشر وحدهم هم الميزات المُسلَّمة.

## 18. Partnership Philosophy — فلسفة الشراكة

نؤمن أن الشراكة يجب أن تُبنى على أربعة أعمدة:

```
   Contribution   +   Expertise   +   Responsibility   +   Measurable Value
   المساهمة           الخبرة           المسؤولية            القيمة القابلة للقياس
```

**المساهمة** — ما يُدخله الشريك فعلًا (خبرة، علاقات، تشغيل، تكنولوجيا، تمويل).
**الخبرة** — معرفة مثبتة في المجال الذي يساهم فيه.
**المسؤولية** — دور واضح ومسؤوليات متفق عليها.
**القيمة القابلة للقياس** — نتيجة يمكن قياسها، لا وعود.

> **بخصوص هيكل الشراكة:**
> **Partnership structure to be discussed and agreed based on the partner's contribution, role, responsibilities and strategic value.**
>
> لم تُحدَّد في هذه الوثيقة أي نسب ملكية أو حصص أو شروط مالية. هذه الوثيقة تفتح باب النقاش ولا تحسمه.

## 19. Roadmap — خارطة الطريق

خارطة منطقية بلا تواريخ أو أرقام غير موجودة في المشروع:

### Phase 1 — Platform Validation / Demo / Technical Stabilization
**الحالة: جارية — منجزة إلى حد كبير.**
المنصة تعمل وتُختبر: وظائف أساسية مبنية ومختبرة، عرض تجريبي عام متاح، بوابات الجودة (Typecheck / Tests / E2E / Build) تمرّ.

### Phase 2 — Production Readiness / Legal / Providers
**الحالة: التالية.**
تكوين مزوّدي الدفع والصرف والبريد والرسائل وAI، البنية التحتية المستضافة، الوثائق القانونية (شروط، خصوصية، استرداد، اتفاقية بائع، DPA)، إجراءات KYC/KYB وAML، والمراجعة الأمنية.

### Phase 3 — Initial Market Launch
**الحالة: مخطط.**
إطلاق أولي منضبط في سوق محدّد بقطاع محدّد، مع مزوّد دفع إنتاجي ودعم عملاء وإجراءات تصعيد.

### Phase 4 — B2B Growth
**الحالة: مخطط.**
توسيع قاعدة المورّدين والمشترين، تشغيل العلاقات B2B، وتحويل الطبقة الذكية (AI) إلى قيمة تشغيلية مباشرة.

### Phase 5 — International Expansion
**الحالة: مخطط.**
فتح أسواق ودول جديدة **تدريجيًا**، كل سوق بجاهزيته التشغيلية والقانونية الخاصة.

## 20. Key Risks & Considerations — المخاطر والاعتبارات

لا نخفي المخاطر. إظهارها يدلّ على إدارة واقعية للمشروع.

| المخاطرة | الوصف | كيف تُدار / ما يحتاج دراسة |
| --- | --- | --- |
| **Legal / Regulatory** | غياب الوثائق القانونية وتنظيم الوساطة والدفع يمنع الإطلاق التجاري | Phase 2: صياغة الشروط والخصوصية والاسترداد واتفاقية البائع وDPA + مراجعة تنظيمية |
| **Payment** | مزوّد الإنتاج غير مُهيّأ؛ الاعتماد على مزوّد واحد خطر تشغيلي | تكوين مزوّد إنتاجي + خطة مزوّد بديل + اختبار Webhooks والاسترداد فعليًا |
| **KYC / KYB** | لا توجد إجراءات تشغيلية ولا كود مخصص للتحقق من الهوية/الكيان | تصميم إجراءات KYC/KYB وربطها بمستويات التوثيق القائمة |
| **AML / PEP / Sanctions** | لا فحص لقوائم العقوبات أو الأشخاص السياسيين | دراسة المتطلبات التنظيمية لكل سوق قبل الإطلاق |
| **International Operations** | التوسع الدولي يتطلّب التزامًا قانونيًا وضريبيًا لكل دولة | إطلاق تدريجي لكل سوق على حدة، مع مراجعة قانونية محلية |
| **Logistics** | WASIT ليست طرفًا لوجستيًا؛ الشحن خارج نطاقها | تحديد حدود المسؤولية بوضوح + شراكة لوجستية اختيارية |
| **Market Adoption** | لا يوجد بعد دليل على اكتساب مستخدمين حقيقيين | Phase 3: تجربة إطلاق محدودة + قياس فعلي قبل التوسع |
| **Security** | لم تُجرَ مراجعة أمنية إنتاجية أو اختبار اختراق | مراجعة أمنية مستقلة قبل الإنتاج + تفعيل المراقبة والتنبيهات |
| **Provider Dependency** | الاعتماد على مزوّدي دفع/AI/بريد خارجيين | طبقة تجريد مزوّد-محايدة موجودة أصلًا (Provider-agnostic) تقلّل الالتصاق |
| **Financial Model** | بعض القرارات المالية (من يتحمّل رسوم الدفع، آلية التحصيل) غير محسومة | حسمها تجاريًا في Phase 2 قبل الإطلاق |
| **Latent inconsistency** | تعليق توثيقي في محرّك العمولة يذكر ترتيبًا تصاعديًا بينما الاستعلام تنازلي | لا تأثير حاليًا (سياسة واحدة فقط)؛ يجب حسم النية قبل إضافة سياسة ثانية |
